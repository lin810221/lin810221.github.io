把顏色理解成帶有編碼與範圍的座標，實際比較灰階、HSV 與照明改變造成的資訊差異。

## 顏色不是物體固定不變的數字

一個紅色物體在相機上得到的像素，會受照明、曝光、白平衡、感光元件與壓縮影響。RGB 是三個通道的表示方式，並不保證同一物體在所有照片都得到同一組數值。因此「找紅色」需要先定義來源條件與容許變化，不能只挑一個 RGB 值做相等比較。

先用紅、綠、藍、灰四張合成色塊建立直覺：紅色 `(255,0,0)`、藍色 `(0,0,255)` 在 RGB 與 BGR 解讀時會互換；灰色 `(128,128,128)` 卻看不出通道顛倒。稽核資料時應包含能暴露差異的案例，而非只測剛好不受影響的圖片。

## 灰階會保留什麼

常見 8-bit RGB 灰階轉換近似使用加權和，例如 $Y'=0.299R'+0.587G'+0.114B'$。這裡的撇號提醒我們是編碼後的通道，所得是便於顯示或分析的灰階值，不可不加說明便當作物理亮度。嚴格線性光計算涉及去除 gamma 與指定色彩標準。

以純紅與純藍算例，灰階約為 76 與 29；不是三通道等權平均的 85。轉成灰階能減少資料量，也會丟失區分紅綠指示燈等任務所需的色彩資訊。若兩類只差顏色而亮度相同，灰階前處理可能讓任務變得無法辨識。這是資訊被移除的結果，並非模型容量不足。

## HSV 為何有時容易設規則

HSV 用色相 H、飽和度 S、明度 V 表示顏色。你可以把「有足夠飽和度的藍色」寫成一段色相範圍，通常比三個 RGB 通道各設門檻更容易理解。但它不是照明不變表示：強反光、陰影與低飽和度都可能使規則失效，接近灰色時色相也不穩定。

OpenCV 一般 uint8 HSV 的 H 常用 0–179，S、V 為 0–255；浮點輸入的範圍與其他函式庫可能不同。紅色位在色相圓的接縫，規則可能需要接近 0 與接近上限的兩段範圍。不可直接把繪圖軟體的 360 度或 0–1 色相數值原封不動塞進 uint8 閾值。

## 用人工色塊檢查 API

以下是獨立的 OpenCV 色彩轉換示意，不使用相機、外部圖片或 GUI。因為來源已知是 RGB，轉換旗標必須寫 RGB，而非沿用習慣的 BGR。

```python
import numpy as np
import cv2

rgb = np.array([[[255,0,0], [0,255,0], [0,0,255]]], dtype=np.uint8)
gray = cv2.cvtColor(rgb, cv2.COLOR_RGB2GRAY)
hsv = cv2.cvtColor(rgb, cv2.COLOR_RGB2HSV)
print(gray.tolist(), hsv.tolist())
blue = cv2.inRange(hsv, (100,100,60), (130,255,255))
assert blue.tolist() == [[0,0,255]]
```

這組藍色門檻只示範合成色塊的規則，不是所有相機與場景的推薦值。`inRange` 的輸出是選取遮罩；其中 255 表示選中，與語意分割教材的 ignore label 255 是不同用途。使用同一個數字時，要看資料在流程中的角色。

## 如何選擇與評估

先問顏色是否與答案有因果上合理的關係，再設比較實驗。對相同資料切分比較 RGB、灰階與簡單 HSV 規則，按照光源、相機及類別分組觀察錯誤。若 RGB 模型依背景顏色猜答案，它可能在隨機切分表現很好，換新背景就失敗。此時應改進資料設計，而不是宣稱模型已學會物體形狀。

HSV 與 Lab 等色彩空間是重表達或轉換，不是萬能特徵。轉換若依賴色彩標準、輸入範圍及白點，部署也必須一致。不要把某種色彩空間稱為永遠更準；有效性要由任務、成像條件與獨立測試共同決定。

## 練習與解析

**題目：** 兩類產品外型相同，唯一差異是紅色／綠色標籤；將資料轉灰階是否一定有利？一張白色物體的 HSV 色相落在藍色範圍，又是否能直接判成藍色？

**解析：** 灰階可能移除關鍵顏色訊號，需先看轉換後仍可辨識否。白色物體飽和度低，色相數字不足以代表穩定顏色；規則至少要一起檢查 S、V，並用實際部署照明驗證。保留原始 RGB 圖，讓前處理選擇能重做與比較。
