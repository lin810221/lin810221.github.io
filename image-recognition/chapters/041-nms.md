## 三個門檻各自決定不同事情

信心門檻決定哪些預測值得保留；NMS的IoU門檻決定哪些重疊預測視為重複；評估的IoU門檻決定預測能否算命中真實框。三者雖常都寫成0.5，意義完全不同。修改其中一個後，應記錄更動位置與理由，不把所有參數稱作「準確度」。

模型分數通常是排序依據，未必是經過校準的正確機率。 `score=0.9` 不自動代表這類框在所有場景有90%正確率。分數過濾也不能修復幾何錯誤：一個高分但框錯位置的預測，仍可能在評估中是FP。

## 逐步做一次NMS

同類三個框：A=`[0,0,10,10]`、分數0.9；B=`[1,0,11,10]`、分數0.8；C=`[20,0,30,10]`、分數0.7。A與B交集90、聯集110，IoU約0.818；A與C不相交。若NMS門檻0.5，先保留A，抑制B，再保留C。結果是A、C。

若先把信心門檻設0.75，C根本進不了NMS，結果只有A。若信心門檻0.6、NMS門檻0.9，A和B都保留，結果三框。較大的NMS門檻一般容忍更多重疊；較大的信心門檻則移除更多低分預測，兩者方向不可混淆。

```python
import torch
from torchvision.ops import nms, batched_nms

boxes = torch.tensor([[0.,0.,10.,10.], [1.,0.,11.,10.], [20.,0.,30.,10.]])
scores = torch.tensor([.9, .8, .7])
keep = nms(boxes, scores, iou_threshold=.5)
assert keep.tolist() == [0, 2]
classes = torch.tensor([1, 2, 1])
keep_by_class = batched_nms(boxes, scores, classes, iou_threshold=.5)
assert keep_by_class.tolist() == [0, 1, 2]
```

這個例子的分數互不相同，便於清楚追蹤排序。完全同分且重疊的框在不同裝置可能選出不同索引；若重現政策需要穩定tie-break，要另外明定，不冒稱所有CPU/GPU情境都位元相同。

## 為什麼通常要分開類別

一個人拿著背包，人的框和背包框可高度重疊，卻不是同一個物件。class-aware NMS只在相同類別內抑制；class-agnostic則忽略類別。選擇後者應有任務理由，例如互斥類別的去重政策，而不是因為呼叫比較簡短。

同一類的兩個人靠很近，也可能有高IoU。一般hard NMS無法知道那是重複預測還是真實擁擠；提高門檻可能保留兩人，也可能增加重複框。應在密集場景的驗證切片比較，必要時考慮soft-NMS或不同模型設計。不要只挑一張看起來最好看的照片決定門檻。

## 評估前的分數截斷要謹慎

畫面上只展示高分框是一種產品政策；建立PR曲線則需要足夠廣的分數範圍。先以0.9砍掉大量預測，再宣稱模型召回很低，可能只是評估前處理過度截斷。正式評估依協定保存原始分數、類別、座標與每圖預測上限，確保可以重算。

部分偵測器已在forward內做NMS與候選數截斷。應先閱讀輸出契約，不盲目再做第二次NMS；集合預測架構也可能依其訓練設計直接輸出集合，不適合把所有模型的後處理硬改成同一條管線。

## 練習與解析

如果A與B的IoU剛好等於門檻0.5，Torchvision的`nms`是否抑制B？API定義為大於門檻才抑制，所以僅等於不會因這個條件被刪。浮點接近邊界時仍要以實際精度驗證。這也說明測試不能只驗證0.8這種遠離邊界的例子。

進一步設計四類案例：不同類但重疊、同類且重疊、完全不相交、完全同分。把保留索引、分數政策與類別策略寫在預測檔metadata，之後才有辦法比較版本。
