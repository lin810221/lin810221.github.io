## 什麼時候需要改寫

使用者說「住飯店能花多少」，文件寫「國內出差住宿費上限」。兩者可能同義，但字面重疊少。查詢改寫的工作是協助檢索，而不是在還沒找到資料前先宣告答案。

最安全的起點是受控詞典與縮寫展開，保留原查詢，另加一個或數個變體。例如把「住飯店」展開成「住宿費 上限」，但不要擅自加入「國內」，除非上下文已確定地區。教材中的詞典只是虛構規章資料的示範。

## 三種方法的區別

| 方法 | 產生什麼 | 用途 | 風險 |
| --- | --- | --- | --- |
| Rewrite | 一個獨立、完整的問題 | 去除口語與代名詞 | 改掉限制條件 |
| Multi-query | 多個同意圖表述或子問題 | 增加候選覆蓋 | 查詢成本與偏題 |
| HyDE | 假想的回答型文件 | 作為檢索表示 | 假想細節被當成事實 |

HyDE 研究使用模型生成假想文件，再用其表示做檢索。關鍵是這份假想文字只幫助搜尋，不是最終可引用的證據。[HyDE 論文](https://arxiv.org/abs/2212.10496)

## 硬條件不能隨改寫漂移

產品型號、日期、國家、單位、否定條件與身分範圍應分開保存。若問題是「不包含國際出差」，改寫不得變成「國際出差住宿」。對代碼搜尋，同時保留精確原文查詢，避免把型號全部改成通用概念。

```json
{
  "original_query": "2026 年國內出差住飯店能花多少？",
  "retrieval_queries": ["2026 國內出差 住宿費 上限"],
  "filters": {"region": "domestic", "year": 2026},
  "must_preserve": ["2026", "國內"]
}
```

這是應用程式資料契約。模型提出的 filter 必須經過 schema 與授權驗證，不能讓改寫器擴大使用者可見範圍。

## 如何控制額外成本

設上限，例如最多三個變體；保留每路查詢與來源排名；融合前對重複變體去重。對本來已有精確代碼的問題可以不改寫。若變體帶來的候選品質下降，回到原查詢基線，而不是無限增加搜尋輪數。

要分開測「重寫是否保留意圖」與「重寫是否改善召回」。一個文法更漂亮的問題，可能反而刪掉關鍵年份。變體中出現的數字若沒有來自原問題或受信資料，就應特別檢查。

## 練習與參考答案

**題目：**HyDE 產生「住宿上限 3000 元」，實際檢索文件是 2400 元，最終回答應用哪個？

**參考答案：**只能根據適用的真實文件回答 2400 元，並引用真實片段。假想文件應留在 query transformation 的診斷資訊中，不加入可引用來源。如果它讓系統偏向錯誤文件，應改寫或停用這一路徑。
