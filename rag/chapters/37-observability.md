## 為什麼最後答案不夠

當使用者說回答錯了，你需要知道當時看到哪份資料、如何排序、context 有什麼、模型是否完成。只有答案字串無法重現當下流程，尤其索引和模型會持續更新。

每次請求分配 request ID，跨身分驗證、查詢改寫、檢索、重排與生成傳遞。每一段記錄開始、結束、狀態與必要的版本，讓你能定位最早出錯的位置。

## 最小 trace 欄位

```json
{
  "request_id": "req-123",
  "corpus_version": "2026-10-a",
  "retriever_version": "bm25-v1",
  "candidate_ids": ["chunk-a", "chunk-b"],
  "context_ids": ["chunk-a"],
  "answer_status": "answered",
  "latency_ms": {"retrieve":12, "generate":850},
  "usage": {"input_tokens":400, "output_tokens":90}
}
```

如果要保存完整問題、證據與答案，先決定授權、保留期限、遮罩與刪除規則。不能因為是 debug 就永久複製所有私人文件。API Key、Authorization header 和可直接讀取私人來源的臨時憑證不應進入日誌。

## 線上監控看什麼

系統面看成功率、timeout、限流、各階段延遲與索引工作失敗；資料面看文件數、版本分布、空文字、維度不符、查詢無候選率；品質面看引用缺失、拒答率與抽樣人工審查。

拒答率變高可能是知識庫缺資料，也可能是權限配置錯誤、來源刪除或門檻太嚴。指標應附可追查的樣本，不能只在 dashboard 用紅綠燈下結論。

## 使用者回饋怎麼用

「有幫助」和「正確」不是同一個標籤。回饋可分找錯文件、內容過期、回答誤解、引用錯誤、需要更多資訊。把高影響案例加入經審核的回歸題集，再修資料或程式。

不要把使用者隨手更正的文字直接寫進正式索引作為新規則。先保存回饋來源、審核狀態與適用範圍，避免錯誤或惡意回饋污染全體使用者知識。

## 重現與版本

如果無法保存全部文字，可以保存來源版本、片段 ID 和受控快照位置。若來源已刪除或模型不再提供舊版本，應誠實標示重現限制；不要把相同 prompt 但不同 corpus 的執行稱為完全相同實驗。

## 練習與參考答案

**題目：**監控看到答案正確率下降，但沒有任何 API 錯誤，該查什麼？

**參考答案：**比較部署前後的 corpus、chunker、encoder、prompt 與權限版本；抽樣查看候選與 context。功能可用不代表內容品質正常，資料更新與查詢分布漂移都可能在 HTTP 200 下造成品質下降。
