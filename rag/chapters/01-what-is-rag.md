## 先從一個真實需求想起

你想做一個「公司規章問答助理」。使用者問特休要提前幾天申請，但通用模型不一定看過這家公司的規章。即使模型能寫出自然的中文，也不能因此認定它知道正確天數。直接要求「回答要正確」沒有提供事實來源。

RAG 是 Retrieval-Augmented Generation，通常翻成檢索增強生成。核心做法是先從外部資料取得與問題相關的證據，再把證據連同問題交給生成模型。經典 RAG 論文研究的是把參數化模型與可檢索的非參數記憶結合；本課程學的是現代系統工程中的文件檢索與問答流程，不會把一般 API 串接說成已重現論文的聯合訓練。[原始論文](https://arxiv.org/abs/2005.11401)

## 三個字母各自負責什麼

| 階段 | 工作 | 可以失敗的方式 |
| --- | --- | --- |
| Retrieval | 找出候選文件與片段 | 找到舊版、漏掉例外、跨租戶取資料 |
| Augmentation | 把證據放進本次模型輸入 | 內容被截斷、來源編號接錯、預算不足 |
| Generation | 依證據整理答案 | 誤讀否定句、捏造數字、引用不支持主張 |

因此，RAG 是一條可以拆開診斷的資料流程。當回答「提前五天」而文件寫三個工作日，第一步應檢查檢索到的片段；如果片段正確，再檢查生成，而非同時更換所有元件。

## 一個完整的小例子

問題是「特休申請要提前多久？」文件是「特休申請必須提前三個工作日提出，並由直屬主管核准。」檢索器找到這句，組裝器加上 `[S1]`，生成器回答「須提前三個工作日，並由直屬主管核准。[S1]」。來源映射另外保存文件版本與頁碼，使用者才能查證。

如果問題改成「未休特休能換多少錢」，這段資料沒有金額依據。合理行為是說明資料不足，或繼續搜尋對應規章。把三個工作日改寫成三個日曆日、把主管核准省略，都是事實或條件遺失。

## RAG 能改善什麼，又需要什麼

外部知識可以獨立更新，也較容易提供來源；但檢索器只能處理已匯入且當下可見的資料。它不會自動知道文件是否經過批准，也不會保證模型忠實引用。建置時要同時定義資料來源、適用版本、權限、評估題與無答案行為。

本課程把「有根據」拆成三個可測條件：證據有被找到、答案主張受到證據支持、引用能回到正確位置。這三者分開量測，才知道改善發生在哪裡。

## 本課程的實作方式

先用 Python 標準函式庫寫透明的 BM25 檢索和原句擷取，讓你能看見每一步資料。這是完整的離線教學基線，沒有假裝執行 LLM。第 13、14 份範例才提供真正 Embedding 與生成服務的接法。所有公司文件都是虛構教材。

## 自我檢查

**題目：**系統附了三個引用，是否已證明答案正確？

**參考答案：**尚未。引用可能不存在、指向過期文件，或雖然存在卻沒有支持該句主張。應檢查來源身分、版本、適用範圍與主張支持度。學完本課程後，你應能把這些檢查做成資料契約與測試。
