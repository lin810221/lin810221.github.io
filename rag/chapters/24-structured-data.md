## 哪些問題應由資料庫計算

文件檢索擅長找條款，但「十月差旅總額」需要對具體紀錄加總。把所有交易列向量化再讓模型心算，可能漏列、重複或混淆單位。資料庫有精確過濾、聚合與一致性工具，應讓它完成對應工作。

常見架構是文件 RAG 解釋制度，受控 SQL/API 查出實際數據，再讓生成器整理兩者。引用要分開：規則來自文件，總額來自指定時間、幣別與查詢條件下的資料快照。

## 先從參數化固定查詢開始

```python
# sqlite3 示意：參數由 driver 綁定。
rows = connection.execute(
    "SELECT currency, SUM(amount) FROM expenses "
    "WHERE tenant=? AND date>=? AND date<? "
    "AND status=? GROUP BY currency",
    (trusted_tenant, "2026-10-01", "2026-11-01", "approved")
).fetchall()
```

月份採前含後不含的時間區間，並按幣別分組。這些業務定義必須先確定，不能讓模型把未核准支出或多種幣別直接加在一起。Python 官方文件建議用 placeholder 綁定值，避免把輸入組成 SQL 字串。[sqlite3 文件](https://docs.python.org/3/library/sqlite3.html)

## Text-to-SQL 多了一層責任

模型生成 SQL 只是候選程式碼。執行前應限制允許資料表與操作、使用唯讀帳號或受控查詢介面、設定列數與時間上限、驗證租戶條件並阻止不允許的語句。單純用字串檢查 `SELECT` 不等於完整 SQL 安全解析。

對需求固定的助理，可以讓模型輸出查詢意圖與參數，例如 `monthly_expense_total(month, currency)`，由程式執行固定 SQL。這通常比允許任意 SQL 更容易驗收。

## 檢索 Schema 與檢索資料不同

大型資料庫可以先檢索表格、欄位與商業定義，協助模型理解 schema；但這些 metadata 不是交易內容。生成查詢時仍要處理 JOIN 關係、聚合粒度、空值、時區與去重。

例如「訂單數」是訂單表列數、明細列數，還是去重訂單 ID？若定義不同，SQL 可以語法完全正確但業務答案錯誤。測試應有已知結果的小資料集，核對完整查詢語意。

## 回答應附什麼

保存查詢名稱、參數、時間範圍、資料快照時間、幣別與結果。對外顯示可理解的說明，不一定展示原始 SQL；但內部 trace 應能重現。數字由程式格式化，生成器只負責解釋，不重新計算另一個答案。
