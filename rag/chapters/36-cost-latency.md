## 成本分成建置與查詢

匯入成本包含解析、OCR、片段與 Embedding，還有索引儲存；查詢成本包含 query encoder、檢索、重排、生成和可能的重試。文件通常會被問很多次，因此不應每次問題都重新計算全部文件向量。

模型價格、配額和計費單位會變，本課程不寫死單價。實作使用供應商當次 usage 搭配你保存的價格版本，並把單位寫清楚，例如每百萬 input tokens、每請求或每 GB-month。

## 一份可替換價格的估算式

$$
C_q=C_{query\_embed}+C_{search}+C_{rerank}+\frac{T_{in}P_{in}+T_{out}P_{out}}{10^6}+C_{retry}
$$

若價格不是以百萬 token 計，就要換分母與項目。不要把 cached input、工具呼叫和推理 token 一律視為同一價格。輸出預算是上限，不等於實際帳單；精確成本用實際 usage 和帳戶報表確認。

## 延遲看整條鏈

```text
total = auth + rewrite + query_embed + retrieval + rerank + context + generation
```

可並行的 lexical 與 dense 檢索，總耗時接近較慢一路加融合，而不是單純相加；有依賴的改寫與檢索則不能任意並行。記錄各階段時間，才能知道瓶頸在哪裡。

除了平均也看 p50、p95、p99 和 timeout 比率。少數很慢的文件、冷啟動或限流重試會影響使用者體驗；平均數可能掩蓋它們。串流可以改善等待感，但不會自動降低整個答案完成時間。

## 優化順序

先移除每題重建索引，再縮小不必要的候選與重複 context。只對難題使用重排或多輪檢索，快取穩定且授權相容的計算。模型變小或輸入變短後都要重跑品質評估，避免只改善延遲卻失去例外條款。

對大量文件，把未變內容跳過、批次送出可節省匯入；對重排，限制候選與輸入長度可降低推論，但需觀察截斷造成的錯誤。省下計算的同時，保留資料契約與完整性。

## 預算是停止條件

多步 Agent 可設定每題最多工具次數、總 token 或成本上限，達上限回傳部分結果或不足狀態。不要依模型文字「我只再查一次」來控制帳單。重試需有次數上限和抖動，避免同步重試尖峰。

## 練習與參考答案

**題目：**生成只要 1 秒，總回應卻是 8 秒，是否直接換更快生成模型？

**參考答案：**先看分段 trace，可能 OCR、查詢改寫、重排或資料庫等待才是瓶頸。替換占一小部分的生成器改善有限；應先修占比與尾延遲最高的階段，再確認品質未退步。
