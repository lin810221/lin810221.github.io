## 不急著選向量資料庫

先寫出使用者真正要得到什麼。「回答這份二十頁手冊的問題」與「查詢一百萬份文件」是不同的檢索規模；「算出上月營收」與「解釋營收認列規則」需要的證據形式也不同。技術選擇應跟著資料與驗收方式走。

建立需求表時至少記錄：知識多久更新、每次查詢要看多少資料、是否需要精確計算、使用者可看哪些文件、答案是否必須附來源。先定義成功，才有辦法比較方案。

## 四種常見方案

| 方案 | 適合起點 | 需要處理的問題 |
| --- | --- | --- |
| 直接提供全文 | 文件少、一次性分析 | 長度、成本、內容位置與版本 |
| RAG | 文件量大、持續更新、需來源 | 檢索品質、資料管線、權限 |
| 微調 | 穩定格式、風格或特定任務行為 | 訓練集、回歸評估、模型維護 |
| SQL 或結構化 API | 計算、精確過濾、最新交易資料 | Schema、參數、權限、查詢成本 |

微調可以和 RAG 一起使用；例如模型學習輸出格式，RAG 提供最新政策。不要用重新訓練的頻率取代每天更新資料的索引流程。全文輸入也不是品質保證：長上下文研究發現資訊所在位置可能影響使用效果，具體結果仍須在你的模型與任務驗證。[Lost in the Middle](https://arxiv.org/abs/2307.03172)

## 一個可執行的決策順序

先問資料是否已經結構化。如果使用者要精確加總資料庫欄位，優先在資料庫算；如果要解釋制度條款，再檢索文件。接著檢查完整資料是否能以合理成本放入單次輸入。最後評估是否需要重複查詢、多個使用者與不同存取範圍。

例如問「今年已花多少差旅費」，答案應由核准過的支出紀錄加總；問「報銷期限多久」，則由規章文件提供依據。兩個來源可以在同一答案出現，但計算結果與條款要分別附來源。

## 工程成本也要計算

小型知識庫可以先用記憶體線性掃描或本機全文索引。當資料量、延遲或併發要求超過基線，再導入向量服務。對幾十個片段架設分散式叢集，未必比把解析錯誤修好更有效。

比較方案時，固定同一份文件、同一組問題與相同的答案評分標準。若 RAG 版用了新文件而全文版用了舊文件，量到的是資料差異，不能說明架構優劣。

## 本課程採用的路線

本地流程先完成資料讀取、授權、檢索、證據組裝與可查證答案。之後才換掉 Embedding、reranker 或生成器，讓每個元件的效果可比較。一般的 Retrieve → Generate 也可以由 LangGraph 管理；是否增加 Agent 迴圈取決於任務是否需要動態規劃。

## 練習與參考答案

**題目：**有一份五頁的公開菜單，想回答菜品原料；另有每日變動庫存，想知道今天能否供應。如何設計？

**參考答案：**菜單可先全文輸入或小型檢索；庫存應查詢最新結構化資料。不能從上週菜單推測今天庫存。建立相同題目的全文與檢索基線，再用正確率、延遲與維護成本做選擇。
