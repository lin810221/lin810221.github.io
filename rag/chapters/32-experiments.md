## 一次只改可歸因的因素

你同時換模型、改 chunk size、增加 top-k、改 prompt，最後分數提高，無法知道哪個改動有效。建立最小基線，逐步增加一個元件，再保存完整設定與結果。這叫消融或控制比較的思路。

建議順序是先確認資料完整和權限，再比較 chunker、retriever、reranker、context 組裝與生成。上游缺陷會限制下游表現，先調漂亮的回答格式可能掩蓋真正問題。

## 實驗表應保存什麼

```json
{
  "run_id": "rag-dev-017",
  "corpus_version": "2026-10-a",
  "dataset_version": "eval-v2",
  "chunker": {"unit":"char", "size":180, "overlap":30},
  "retrievers": ["bm25"],
  "candidate_k": 20,
  "context_chars": 1200,
  "generator": "offline-extractive",
  "code_commit": "record-your-commit"
}
```

另外保存原始每題輸出，避免只有一個平均分數卻無法重看錯誤。API 模型的實際版本、時間與可重現限制也應註記；不是所有模型都能以相同參數完全重現。

## 一個有次序的比較矩陣

| 實驗 | 改動 | 要看的主要效果 |
| --- | --- | --- |
| A | BM25 基線 | 精確字詞與代碼 |
| B | 加 dense | 同義與跨語 recall |
| C | 加融合 | 各題型的整體覆蓋 |
| D | 加重排 | 前幾名相關程度 |
| E | 改 context | 支持度與輸入成本 |

如果 D 只在訓練過的開發題改善，獨立驗收集沒有改善，可能過度適配。不要重複看驗收題並依它調參後仍稱它是未見測試集。

## 品質、成本與延遲一起看

同一方案可能 recall 較高，但延遲或費用超出需求。畫出每組設定的品質、p95 延遲與每題成本，找出可接受區域。對特定少數難題才啟用多步檢索，也是一種可比較的路由策略。

如果需要判斷小幅差異是否可靠，應看樣本數、題目分組、逐題差異與適當的不確定性估計。十題中多答對一題不宜直接宣稱全面提升一成。

## 把錯誤分到正確階段

檢查原文件是否存在、解析有無保留條款、chunk 是否完整、候選是否命中、context 是否選入、答案是否忠實。把每個失敗分到最早出錯的階段，再依數量與影響排序修正。這能避免所有問題都被歸成「LLM 不夠強」。

## 練習與參考答案

**題目：**增加 top-k 後 recall 提高、答案正確率下降，要怎麼解釋？

**參考答案：**候選覆蓋變好，但新增噪音、重複或衝突可能傷害後續組裝與生成。保留較大召回池，嘗試重排、去重與預算控制，再單獨比較。不能只因 recall 較高就認定整體方案更好。
