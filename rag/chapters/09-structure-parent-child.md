## 找得到與讀得懂是兩個需求

問題只提到某個術語，短片段可能更容易命中；但回答需要前後條件與例外，單一短句又不夠。Parent–Child 設計把索引單位與回傳單位分開：檢索小 child，通過授權後回取較大的 parent。

例如手冊的「國內出差」章節是一個 parent，裡面住宿、交通、報銷各是一個 child。問住宿時檢索住宿 child，再補上章節中的適用地區與生效條件。回取的內容仍須受 context 預算控制。

## 最小資料關係

```json
{
  "child_id": "travel-v3-lodging-1",
  "parent_id": "travel-v3-domestic",
  "doc_id": "travel",
  "section_path": ["差旅規範", "國內出差", "住宿"],
  "version": "v3",
  "text": "住宿上限每晚 2400 元。"
}
```

`parent_id` 不應只用標題組成，因為不同文件可能有相同標題。回取父段落時需匹配租戶、版本與存取政策，不能檢索了新版 child 卻接上舊版 parent。

## 三種補上下文的方法

| 方法 | 索引文字 | 最終證據 | 主要代價 |
| --- | --- | --- | --- |
| 標題前綴 | 標題路徑 + 原文 | 原文與標題 | 可能重複，需保存來源區分 |
| Parent–Child | 小片段 | 父段落或相鄰片段 | 額外讀取與預算 |
| Contextual Retrieval | 為片段補充特定背景 | 原文及可追溯補充 | 預處理成本與摘要錯誤 |

Anthropic 的 Contextual Retrieval 研究描述在索引前為片段加入針對文件背景的說明，並結合檢索方法。這提供一個方向，但效益要在自己的資料集驗證。[官方介紹](https://www.anthropic.com/research/contextual-retrieval)

## 補充文字也有可信度

人工或模型生成的背景並不是原文事實本身。建議把 `original_text` 與 `context_prefix` 分開保存，附上生成方式與版本。最終引用應能回到原始文件；如果補充內容無法由原文支持，不應藉由重複索引而變成看似可靠的證據。

結構感知也包含程式碼、表格和列表。程式碼需要函式簽名與縮排，表格需要欄名與單位，列表需要保留「全部符合」或「擇一符合」的邏輯。把這些結構全部壓成同一種字元窗口，往往會丟失重要關係。

## 實作建議

先在教材的 `Chunk` 加入 `parent_id` 與 `section_path`，建立 parent 字典。檢索結果先依 parent 去重，再選擇回傳範圍。每次回取 parent 都重新執行可見性檢查；若父段落混有更高權限子段落，應重新切分授權邊界，或只回傳允許的範圍。

## 練習與參考答案

**題目：**同一 parent 有五個 child 都進 top-5，如何改善資訊多樣性？

**參考答案：**在較大的候選集合上按 parent 去重或限制每份文件數量，再挑選不同來源。不要等最終 top-5 後刪到只剩一段卻不補候選。同時保留多個 child 的命中資訊，讓父段落回取與引用定位仍可追蹤。
