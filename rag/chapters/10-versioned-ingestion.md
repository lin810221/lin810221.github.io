## 更新不是只新增一份文件

規章每次修訂都直接新增到同一索引，卻沒有標記舊版狀態，搜尋就可能把不同時間的規則混在一起。RAG 的知識更新需要一個版本政策：查詢預設看現行版，歷史問題則指定日期或版本。

每次匯入先辨識邏輯文件 ID，再計算內容與 metadata 的變化。若沒有變化，跳過重算；若文字、切塊、Embedding 模型或權限有變化，就執行對應更新。這種同樣輸入重複執行不增加副作用的行為稱為冪等。

## 一份最小 manifest

```json
{
  "doc_id": "travel",
  "source_version": "2026-10",
  "content_hash": "sha256:...",
  "metadata_hash": "sha256:...",
  "parser_version": "text-v1",
  "chunker_version": "char-180-30",
  "embedding_version": "model-and-dimensions",
  "index_state": "ready"
}
```

這些欄位把來源變更與處理方式變更分開。文件文字沒變，但 chunk size 改了，舊片段仍需更新；模型變更也不能只替換查詢向量，留著舊文件向量混用。

## 安全的切換順序

先產生新版本片段與表示，驗證數量、來源、維度與基本檢索。全部成功後，再把查詢指向新版本，最後清理舊版。若底層資料庫不能跨儲存原子切換，可以使用版本指標或狀態欄位，只讓 `ready` 版本可見。

刪除要涵蓋原檔、解析輸出、片段、向量、全文索引、摘要、快取與答案中的可存取連結。不同系統可能是最終一致，刪除後短時間仍可能有殘留結果；例如 OpenAI Retrieval 文件也提醒刪檔存在一致性延遲。使用前應確認服務行為，並在應用層維持可立即阻擋的狀態。[Retrieval 文件](https://developers.openai.com/api/docs/guides/retrieval)

## 先用 SQLite 理解冪等

第 12 份範例的 `upsert_document` 使用 `(tenant,id)` 作為主鍵，digest 包含文字與 metadata。第一次寫入回傳 True，相同輸入回傳 False，版本或角色變動則更新。這是小型文件儲存示範；外部向量索引的批次重建與切換仍要另外設計。

正式更新還需要失敗重試與追蹤。例如某批 100 片段只有 92 片成功，不應宣布整份文件可用。記錄工作 ID、預期片段數、成功數與錯誤類型，允許重試同一批而不產生重複。

## 常見錯誤

只用檔名作全域主鍵會讓不同租戶互相覆蓋；只比較內文會忽略權限異動；先刪舊版再慢慢建立新版會造成服務空窗；快取鍵沒有 corpus version 則可能在更新後繼續回傳舊答案。

## 練習與答案

**題目：**文件內文相同，但存取角色從 reader 改為 hr，是否可跳過？

**參考答案：**不可。必須更新授權 metadata，讓查詢立即排除 reader，並使相關快取失效。是否重算向量可以依系統設計決定，但「不重算向量」不代表「不用更新索引或存取政策」。
