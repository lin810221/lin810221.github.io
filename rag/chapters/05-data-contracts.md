## 為什麼需要明確型別

只用一個字串串接所有步驟，很快就會失去來源。你需要知道一段文字屬於哪份文件、哪個版本、哪一頁、對誰可見。文件、片段、候選與答案的生命週期不同，應使用不同資料結構。

`Document` 是來源文件的標準化表示，`Chunk` 是可檢索的子範圍，`Hit` 是某次查詢對片段的評分，`Answer` 是使用證據後得到的回應。分數屬於查詢結果，不應永久寫成片段的固有品質。

## 最小欄位設計

```json
{
  "chunk_id": "tenant-doc-version-offset-hash",
  "doc_id": "leave",
  "version": "2026-10",
  "text": "特休申請必須提前三個工作日提出。",
  "source": "demo://handbook/leave",
  "page": 2,
  "start": 0,
  "end": 20,
  "tenant": "demo",
  "roles": ["reader"],
  "active": true
}
```

這份 JSON 是欄位示意，offset 必須以實際標準化文字重新計算。`source` 在教材是虛構定位符；正式系統可保存受控文件 URL 或物件 ID，並在開啟原文時再次授權。不要讓模型自行發明來源網址。

## 身分與內容雜湊不同

`doc_id` 表示同一份邏輯文件，版本更新後通常保持不變。`content_hash` 表示內容是否相同。`chunk_id` 可以由租戶、文件、版本、範圍與內容雜湊共同建立，確保不同租戶即使文字相同也不會共用不安全的身分。

角色異動也需要觸發權限更新。若只比較文字雜湊而忽略 ACL，文件從公開改成限制存取後可能仍留在舊索引。教材的更新 digest 包含整份 metadata，讓權限異動也被視為更新。

## 分數與引用各有自己的契約

BM25、cosine、cross-encoder 分數不在同一尺度。`Hit` 可保存 `retrieval_score`、`rerank_score`、`rank` 與 `retriever_name`，不要都叫 `score` 然後直接相加。融合方法在第 16 章說明。

引用映射由應用程式建立，例如 `[S1] -> chunk_id`。回答可以使用 `[S1]`，但映射中的文件版本不能隨生成改變。引用編號存在只驗證結構；主張是否被該片段支持，還需要另一層評估。

## Metadata 不只是裝飾

租戶、角色、有效期間與文件狀態都可能是硬限制。系統應先限制搜尋範圍，再產生候選；資料庫可支援 payload 或 metadata filter，但實際操作語意仍要查明。[Qdrant filtering](https://qdrant.tech/documentation/search/filtering/)

本課程的 `roles` 採「只要與使用者角色有交集即可讀取」；它只是選定的一種 ACL 規則。若業務要求同時具備多種權限，或存在明確 deny 規則，必須修改授權政策，不能直接套用此範例。

## 練習與答案

**題目：**同一文件改了名稱、沒改內文，需要更新嗎？

**參考答案：**通常需要更新 metadata，並視標題是否參與檢索表示決定是否重算向量。若標題影響引用顯示，也要同步對照。內容雜湊、metadata 雜湊和索引版本可分開追蹤，但每種異動都應有處理規則。
