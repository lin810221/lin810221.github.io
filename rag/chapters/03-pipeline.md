## 兩條不同生命週期的管線

建索引管線處理來源文件：取得文件、解析、清理、切塊、產生表示、寫入索引。查詢管線處理使用者問題：驗證身分、理解問題、檢索、重排、組裝證據、生成、檢查與回傳。文件更新時不一定有使用者提問；使用者提問時通常也不需要重建所有文件向量。

```text
來源 → 解析 → 標準化文件 → 切塊 → 表示 → 索引
                                      ↓
問題 → 身分與範圍 → 檢索 → 重排 → 證據 → 回答 → 檢查
```

檢索和生成是不同的計算階段，可以單獨改進；這也是檢索加重排設計常見的分工。[Retrieve & Re-Rank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

## 每一步留下什麼

| 步驟 | 主要輸入 | 建議保存的輸出 |
| --- | --- | --- |
| 解析 | 原始檔與來源資訊 | 文字、頁碼、表格、解析版本 |
| 切塊 | 標準化文件 | chunk ID、offset、父文件、版本 |
| 表示 | 片段文字 | 向量、模型、維度、前處理版本 |
| 檢索 | 問題與身分範圍 | 候選 ID、排名、原始分數 |
| 證據組裝 | 已授權候選 | 最終片段、引用映射、預算 |
| 回答 | 問題與證據 | 答案、引用、狀態、耗用量 |

這些資料讓你能回答：「是不是文件在解析時就消失了？」、「相關片段有進候選嗎？」、「有進候選卻沒有進最終 context 嗎？」沒有階段邊界，最後只剩一個籠統的模型錯誤。

## 同步與非同步怎麼分

初期可以在單一 Python 程式依序執行，降低概念負擔。當 PDF 很大，解析與 Embedding 可放背景工作佇列；查詢端只讀取已完成且可見的索引版本。使用者看到匯入完成之前，系統應清楚顯示處理狀態，不要把「檔案已上傳」當作「已可檢索」。

每份索引可以有 manifest，例如 `corpus_version=2026-10-30-a`、`chunker=char-v1`、`embedding=...`。查詢紀錄保留相同版本，後續才能重現。建置中途失敗時，應繼續服務上一個完整版本，或明確回傳不可用。

## 一次問題的資料流

使用者問特休。伺服器先從已驗證身分得到 `tenant=demo, roles=[reader]`，檢索只看這個範圍。找到五段後，重排選出更直接的兩段；context builder 算上來源標籤和分隔符的預算，產生 `[S1]` 映射。生成器不能改寫映射中的文件 ID。

最後以 `answered`、`insufficient_evidence`、`clarification_required`、`generation_failed` 等狀態區分結果，前端才能呈現對應行為。離線教材另外使用 `extractive_demo`，清楚表示只是擷取原句。

## 練習與驗收

**題目：**每次問問題都重新計算全部文件向量，有什麼代價？

**參考答案：**文件計算重複、延遲與費用增加，也容易因部分失敗造成索引不一致。正式流程在匯入時持久化文件表示，查詢時只算問題表示。教材的 live 小範例為了展示全流程刻意重新計算，不能直接當成生產設計。
