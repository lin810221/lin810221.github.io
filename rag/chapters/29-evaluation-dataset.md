## 沒有固定題集就無法比較

只挑幾個系統擅長的問題展示，無法說明品質。建立一份固定題集，保存每題的目的、相關文件、可接受答案、適用版本與可見範圍。更改模型或切塊後，在同一套條件重跑，才知道改善是否穩定。

至少準備精確代碼、同義改寫、多條件、否定、跨語、版本衝突、權限限制與無答案題。使用者常問的問題與風險高的少數題都需要，不要只按文件容易產生的問句選樣。

## 什麼是 Qrels

Qrels 是 query relevance judgments，記錄問題與候選文件的相關程度。可以是二元相關，也可以是分級：0 不相關、1 有幫助但不完整、2 直接提供需要的證據。分級規則要明確，標註者才有機會一致。

```json
{
  "query": "國內出差住宿費上限",
  "tenant": "demo",
  "roles": ["reader"],
  "corpus_version": "2026-10",
  "relevant": {"travel": 2},
  "expected_facts": ["每晚", "TWD 2400", "國內"],
  "answerable": true
}
```

教材 `data/qrels.json` 只有五題開發用資料，目的是展示指標，不是生產驗收。得到滿分可能只是題目少、用詞與文件高度重疊，不能因此聲稱系統在實際使用有百分之百準確率。

## 標註單位先定義

可以以文件、片段或證據跨度作評估單位。以片段為單位時，切塊策略改動可能讓標註 ID 全部變動；以文件為單位則較穩定，但一份長文件命中不表示已找到真正條款。比較不同 chunker 時，可保存原始證據跨度，再映射到新片段。

有多個可接受來源時，別只把第一份標成正確。否則系統找到等價但未標註的來源會被算錯。對不完整標註，需明確說明評估限制，抽查新系統的未標註命中。

## 分割開發與驗收

開發集用來調參，保留獨立驗收集避免針對已知題過度調整。若同一文件的近乎相同問題散落各集合，仍可能發生洩漏；可以按文件群、時間或業務場景分割，符合真正使用情境。

自動生成問題可以協助擴充，但需檢查答案是否真的在文件、問題是否自然、難度是否多樣，不能讓同一模型出題、作答和評分後就宣布客觀通過。Ragas 研究提供自動評估方向，仍需搭配明確任務與人工校準。[Ragas 論文](https://arxiv.org/abs/2309.15217)
