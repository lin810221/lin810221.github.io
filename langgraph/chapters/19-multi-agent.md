## 先問：真的需要多個 Agent 嗎？

多 Agent 的主要價值可能是隔離上下文、分工開發、工具權限分離或平行處理。角色名稱越多不代表答案越準；同一個錯誤來源也可能被多個 Agent 反覆引用。

如果單一模型加上幾個工具就能完成，先維持簡單。只有在工具選擇混亂、各任務需要大量不同知識，或工作邊界明確時，再考慮拆分。

## 常見的三種架構

| 架構 | 控制方式 | 適合情況 |
| --- | --- | --- |
| Router | 分類後交給特定專家 | 領域明確，路徑大多一次決定 |
| Supervisor | 中央協調者安排專家任務再整合 | 需要多步分派與綜合結果 |
| Handoff | 目前 Agent 把控制權交給另一個 | 對話階段或權限責任轉移 |

這些是設計模式，不是三個必須安裝的類別。可以用一般路由、Send、子圖與 Command 實作。選用額外套件前，先理解自己的狀態及交接契約。

## 一個可推理的任務契約

```python
from typing import TypedDict

class SpecialistTask(TypedDict):
    task_id: str
    question: str
    allowed_document_ids: list[str]

class SpecialistResult(TypedDict):
    task_id: str
    answer: str
    source_ids: list[str]
    status: str
```

協調者提供有限任務及允許資料，專家回傳結果和依據。比起把所有 Agent 的 messages 合成一個列表，這樣更容易驗證資料來源與責任。

## Supervisor 的停止條件

協調者需要明確知道哪些任務已完成、哪些失敗、還剩多少預算。不能只讓它無限判斷「再請一個專家看看」。

可以由程式限制最多三次分派、同一任務不得重複執行，及 token 或時間預算。任務狀態放在 State，真正權限放在工具與服務層。協調模型的自然語言承諾不能成為唯一限制。

## 上下文應該如何流動？

專家應拿到完成任務所需的資料，回傳可被聚合的結果。交接對話時要處理工具訊息配對、來源 ID，以及必要的使用者要求。過多歷史會增加成本，也可能帶進不相關的指令。

檢索 Agent 產生的摘要是衍生資料，不能因為交給另一個 Agent 就自動成為已驗證事實。保留原始文件 ID、版本與引用，讓整合者可以回查。

## 平行專家和一致性

若兩個專家都讀相同的過期文件，兩票一致仍可能錯誤。需要設計的是獨立證據、衝突檢查與確定的整合規則，而不是把多數票當真理。

對於專業分工，可用 Send 平行取得結果；對依賴前一步結論的工作，應保持順序。若某個專家有副作用工具，更要明確處理授權與交接，不應因為父 Agent 能呼叫它就取得全部權限。

## 從簡單路線開始

建議先實作規則 Router：依問題分類到檢索或計算，結果契約固定。再把分類替換為結構化模型輸出；最後才引入協調者的多輪規劃。每一步都有可測行為，出錯時才知道問題增加在哪一層。

**練習：**設計兩個專家「文件查詢」和「計算」，寫出各自可使用的工具清單與回傳格式，並說明協調者如何判斷工作完成。
