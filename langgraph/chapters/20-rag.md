## RAG 在解決什麼？

Retrieval-Augmented Generation 先取得與問題相關的外部資料，再讓模型依資料回答。LangGraph 負責串起檢索、檢查與回答的控制流程；它本身不是向量資料庫，也不會替所有檢索結果保證正確。

```text
問題 → 正規化 → 檢索 → 有足夠依據？
                       ├─有→ 草稿 → 引用檢查 → 審核 → 回答
                       └─無→ 澄清或拒答
```

這條路徑中，檢索失敗、查無資料、文件不足與模型生成失敗應是不同狀態，才能適當處理。

## 建立檢索資料流程

正式 RAG 通常先離線處理文件：載入、切塊、保留 metadata、產生索引、設定版本，再於執行時查詢。Chunk 應盡量保留足夠語境；切太小失去條件，太大可能稀釋相關內容並增加 token。

每段資料至少保留 document_id、chunk_id、來源位置及版本。查到一段文字卻不知道原始來源，後續很難校正或更新。

| 檢索方式 | 擅長 | 常見限制 |
| --- | --- | --- |
| 關鍵字 / BM25 / TF-IDF | 精確詞、代碼、產品名 | 同義改寫可能漏掉 |
| 向量檢索 | 語意相近的敘述 | 相似不代表事實或條件相符 |
| Hybrid | 結合詞彙和語意訊號 | 需設計融合與評估方式 |
| Reranker | 重新評估候選的相關性 | 增加成本及延遲 |

## 檢索分數怎麼用？

相似度取決於 embedding、距離度量與資料分布。不要假設不同資料庫的 0.8 都代表八成正確，也不要直接把它當成模型答案信心。用有標註的查詢集調整 top-k、篩選條件與門檻。

正規化查詢可協助檢索，但要保留原始問題。若把具體規格或否定詞刪掉，召回可能更廣，答案卻更不符合原問題。

## 產生答案與引用

把文件以穩定的 ID 傳入模型，例如 `[D1]` 對應特定 chunk。要求依據資料回答並標示來源，且在沒有依據時明確說明不足。

模型可能編造 `[D9]`，因此程式應驗證引用 ID 確實來自本輪檢索。這只能驗證引用存在，**不能保證引用內容真的支持整句答案**。語意支持仍需更進一步評估或人工審核。

把文件當資料而不是新指令。文件裡的「忽略前面規則」或「呼叫寄信工具」不能改變應用權限。生成與執行有副作用的工具應分開控制。

## 有必要做 Agentic RAG 嗎？

若需要反覆改寫查詢或搜尋多個資料源，可讓圖循環「檢索 → 評估 → 改寫」。但每輪都要有上限，並記錄已查過的內容。對固定知識庫，一次檢索加明確拒答通常更容易驗證。

第一版先用關鍵字檢索和固定模板，測通狀態、引用與拒答路徑；第 25 章就是這樣的可執行基線。之後替換 retrieval 或 generation，流程契約維持穩定。

## 評估不能只看答案像不像

至少分別量測召回是否包含必要文件、答案是否受到來源支持、引用是否正確、無答案時能否拒答，以及時間與費用。生成品質差有時是檢索漏資料，先定位再改模型。

**練習：**準備三題有答案及兩題無答案的問題，寫出預期文件 ID 和應採取的路徑。這份小資料集比只測一個順利案例更有幫助。
