# Elasticsearch 與 OpenSearch：選型與相容性的界線

辨識產品、版本與服務差異，用能力清單選擇，而非把名稱相近當成可直接互換。

## 同源不代表現在完全相容

Elasticsearch 與 OpenSearch 是不同產品，版本、向量引擎、DSL、SDK、授權與雲服務功能都各自演進。本課可執行的請求配方以 Elasticsearch 9.5 為目標，不保證直接送到 OpenSearch 就能得到相同語意。遷移應明確選定來源版、目標版與部署方案。

## 以查詢能力比對

| 要求 | 實際需要檢查 |
|---|---|
| 中文與多語 | Analyzer、外掛、雲服務是否允許安裝 |
| 向量 Filter | Filter 在 ANN 哪個階段生效、候選不足如何處理 |
| Hybrid / RRF | API 結構、版本、功能授權與排序行為 |
| 高可用 | 分片、副本、故障切換與跨區策略 |
| 維護成本 | 升級路線、監控、支援與資料搬移 |

不要因 SDK 支援一個參數，就推論目前伺服器版本或方案已啟用對應能力。雲服務可能限制外掛、端點與管理權限；功能授權也可能變更，規劃採購時再查當下官方條件。

## 相容性驗收清單

以同一來源快照建兩邊索引，記錄 mapping 差異、token 序列、query DSL、Filter 與排序；跑精確代碼、多語、零命中與高基數條件。再比較更新後可見性、刪除、分頁與故障恢復。分數值不同不一定是 bug，相關性與業務資格才是可共同定義的驗收目標。

## 不把換引擎當第一個排錯步驟

若漏查原因是來源缺資料、token 不相容或錯誤 tenant，換資料庫通常無法修好。先建立可重現的小例與 Exact/文字基線，確認瓶頸屬於能力或規模，再評估遷移。保留來源與可重建 ingestion，會比把所有業務邏輯綁在某一份 DSL 更容易演進。

## 記錄決策

決策文件應寫出必需能力、已測工作負載、版本、資源與未驗證限制，列出可接受的替代方案。這份記錄的價值是未來需求變更時能重做比較，不是宣稱某個產品永遠最強。後面完整專題以可替換的候選介面示範這種分工。

## 練習與解答

**請先嘗試：** 用 Elasticsearch Python client 連到 OpenSearch，健康檢查成功就算相容嗎？

不算。需驗證實際 API、查詢與寫入語意、認證、版本及支援策略；官方各自 SDK 通常更符合各產品的契約。健康端點只證明該次回應，不能代表所有功能可互換。
