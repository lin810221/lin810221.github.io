# 來源、索引與查詢服務：資料走過哪幾層

把搜尋拆成資料流與查詢流，避免把索引當成唯一真相。

## 來源資料與衍生索引

來源儲存文件本體、業務主鍵、租戶與版本。倒排索引儲存詞到文件的位置；向量索引儲存表示及鄰近關係。兩者通常可以從來源重建。當來源 revision=3 而向量 payload 還是 revision=2，查詢命中並不能證明它仍可顯示。

```text
寫入：資料驗證 → source + outbox 同一交易 → worker → search index
讀取：可信身分 → query plan → scoped candidates → source hydration → ranking
```

索引保存的 title 可能只是展示快取。若更新尚未同步，必須決定回來源讀最新內容、暫時隱藏候選，或明確接受已定義的延遲。本專題採回來源比對版本，不把舊內容默默當新內容。

## Ingestion 不只是 insert

匯入流程要正規化欄位、產生穩定 ID、檢查維度、紀錄表示 recipe，並回報每一筆失敗。ETL 可能是全量批次，也可能是 CDC 增量；查詢服務不應直接承擔每次昂貴重建。先寫出可重送的小批次，再考慮平行 worker。

## 查詢計畫的責任

身分系統提供 tenant；使用者只提供 query 與有限的 k。查詢計畫選擇精確代碼、文字、向量或多路候選，為每路設定上限與逾時。Filter 應盡可能在每一條召回路徑生效；融合後仍要逐筆檢查權威來源。事後檢查不能讓已被未授權候選擠掉的有效資料自動回來。

## 觀察每一層的失敗

| 現象 | 優先檢查 | 可驗證的證據 |
|---|---|---|
| 完全無命中 | 斷詞、索引可見性、Filter | token、索引計數與查詢 body |
| 命中舊版本 | 同步延遲、checkpoint | source/index revision 與事件 seq |
| 很慢但 CPU 不高 | 排隊、網路、磁碟 | 分段延遲與連線池等待 |
| 不同租戶互見 | 身分與每路 Filter | 兩租戶同查詢的負向驗收 |

把 query_id、資料版本、候選數與各階段耗時一起紀錄，比只保存最終分數更能定位問題。日誌不需保存機密文件全文；可使用受控的查詢分類與匿名識別。

## 練習與解答

**請先嘗試：** 向量庫已備份，能否刪除來源資料庫來節省空間？

<details><summary>展開解答與判斷依據</summary>

不行。是否能重建來源取決於完整資料契約，而本課向量庫只存 ID、Filter 與版本，不含完整權威本文。備份策略應分別處理來源、事件與可重建索引，並實際演練還原。

</details>
