# ETL 與批次匯入：讓錯誤可重跑、可對帳

從原始文件到可查索引，安排驗證、分批、錯誤隔離與水位紀錄。

## 匯入管線的順序

讀來源快照→解析→正規化→驗證 schema→分配穩定 ID→建立表示→寫入索引→對帳。不要在前面丟棄 revision、tenant 與來源定位，最後再用模糊比對補回；這會讓更新與刪除難以可靠對應。原始資料保存與索引內容需有可追溯的契約。

## 有界批次與背壓

批次太小有呼叫開銷，太大會增加記憶體、逾時與重試成本。以文件數與 bytes 雙上限切批，限制同時在飛請求，當下游慢就減速。embedding 或大型本文可使單筆很大，只限制1000筆不足以控制容量。記錄來源區間、批次 ID 與成功/失敗數。

## 錯誤分流

| 類別 | 例子 | 處理 |
|---|---|---|
| 永久資料問題 | 錯維度、非法 ID、schema conflict | 隔離並修正，不無限重試 |
| 暫時資源問題 | 服務忙碌、短期 timeout | 有界退避，先確認冪等 |
| 權限問題 | 憑證無效、索引不允許寫入 | 停止該作業並回報 |
| 版本問題 | 舊 revision、同版不同內容 | 依來源契約拒絕或人工釐清 |

## 計數只是第一層驗收

來源1000筆、索引1000筆仍可能 ID 對錯。比對可查 active 數、每租戶數、ID 集合、版本、recipe 與抽樣內容，再跑代表性 query。刪除標記、重複 chunk 與重試覆寫都會讓單純 count 誤導。保存來源 snapshot/watermark 與 manifest，才有辦法重建同一批索引。

## 本課實作的範圍

虛構十筆 fixture 很小，目的是把契約與故障窗口看清楚，不是大規模 ETL benchmark。你可以在複製資料後練習分批，但應保持 ID 與租戶規則、另作清楚的容量實驗。正式匯入需在目標服務驗證背壓、每筆錯誤與儲存容量。

## 練習與解答

**請先嘗試：** 匯入器遇到一筆錯維度，是否整批吞掉錯誤繼續？
