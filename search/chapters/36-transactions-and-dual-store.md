# 單庫交易與雙庫同步：何時需要 Outbox

比較來源與索引在同一交易內外的差異，避免把兩次成功呼叫誤當原子提交。

## 同一資料庫內的原子性

若文字、metadata 與向量在同一 PostgreSQL 交易更新，讀者可依隔離級別看到一致提交；但慢模型計算、外部服務與檔案操作不會自動加入交易。外部 embedding 可先算好，再以條件 revision 寫回，或透過背景工作完成，避免長時間鎖住業務資料。

## 雙寫的失敗窗口

先寫來源成功、再寫搜尋庫失敗，索引落後；反過來先寫索引、來源失敗，索引出現沒有權威來源的資料。網路逾時也可能表示請求已成功，只是回應沒收到。兩次 API 都有成功回應，不會讓中間故障窗口消失。

## Outbox 與 CDC

將來源資料與 outbox event 寫在同一交易，worker 之後讀事件更新索引。CDC 可從資料庫變更紀錄取得事件，減少應用漏送，但仍需處理保留期限、順序、schema、重送與消費水位。兩者不是天然 exactly-once；索引寫入需要穩定 ID、版本及冪等策略。

## 查詢如何面對延遲

索引提供候選，服務回來源查最新資格。active 變更可立即隱藏，但候選位置仍被舊資料占用，召回可能暫時下降。因此要監控 lag、失效候選比例與零結果，並定義更新 SLA。若產品要求寫後讀一致，可能需要等待特定水位或採用單庫查詢，不能只靠口頭承諾。

## 選擇需要付出的成本

單庫減少同步系統，卻要管理共享資源與索引維護；雙庫可隔離負載與採專用能力，卻增加 ingestion、事件與恢復流程。決策應以實際查詢能力、更新率、團隊維運與故障預算作比較。本課專題選雙庫是為了實作這些問題，不表示每個專案都應照搬。

## 練習與解答

**請先嘗試：** 來源提交後，worker 更新向量成功，但在保存 checkpoint 前當機，會怎樣？

<details><summary>展開解答與判斷依據</summary>

重啟後會重送同一事件。穩定 point ID、版本判斷與冪等 upsert/delete 讓重送不產生重複效果；只有在索引寫入完成後才推進 checkpoint。本課會注入這個故障並驗證。
