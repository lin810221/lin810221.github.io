## 向量不是孤立的浮點數

每一筆向量至少需要來源 ID、表示設定與內容版本。只有 `[0.1,0.2,...]` 沒有足夠資訊判斷可否和 query 比較。把它當成有 schema 的資料，更新與除錯才有依據。

教材 `EmbeddingSpec` 包含 provider、model、revision、dimensions、query/document recipe、正規化與前處理。正式 manifest 還可加入 pooling、dtype、資料版號與模型檔雜湊。

## 設定指紋

對設定作穩定序列化再雜湊，可得到指紋。它方便比較是否相同，但不證明設定是真實的：若你寫「l2」卻沒有正規化，指紋只會穩定記錄錯誤。需要匯入驗證一起確認。

## 快取分層

文件向量 cache 依賴來源內容與 document recipe；問題向量 cache 依賴 query recipe；檢索結果還依賴索引版本與授權範圍。不要把它們混成只看文字的一個 cache。

教材 `cache_key(text,spec,role)` 示範表示層差異。正式服務仍要套用資料存取政策；即使能共享計算，也不能因此共享其他人的原文或結果。向量可能含敏感資訊，第 42 章會說明。

## 原文與向量的連結

保存文檔版本、chunk ID 和 offset，更新時只讓相容版本可見。內容變了、parser 變了或 chunk 邊界變了，都可能需要重新計算。權限改動則需立即更新可見性與衍生結果，不一定重算向量，但不能忽略。

## 讀寫驗證

寫入前確認維度、有限數值、必要的非零方向與正規化誤差；讀取時驗證 manifest，避免另一個程式使用不同設定寫入。二進位或量化儲存還要保存 dtype、endianness 或 scale 等解碼資訊。

向量資料庫可提供這些欄位中的一部分，應用仍需定義語意。資料庫接受 payload 不代表它會自動檢查模型 recipe。

## ID、內容與表示指紋各管什麼

文件 ID 表示邏輯身分，內容雜湊表示原文有沒有改，設定指紋表示如何編碼。三者不互相取代。相同文件更新文字，ID 可以不變，但向量內容要改；不同文件文字相同，可能共享計算卻仍有不同授權與來源。

若只用 ID 快取，文字更新會讀到舊向量；只用內容雜湊又可能忽略 recipe；只用維度則更無法分辨模型。把依賴分清楚，才能實作安全失效。

## 練習與參考答案

**題目：**同一句話、同模型、同維度，只把 query 前綴改了，要使快取失效嗎？

**參考答案：**要把它視為設定變更。結果可能不同，cache key 需反映 recipe；再決定文件側是否相容、是否要重建索引。不能只因向量長度一致就繼續用舊結果。
