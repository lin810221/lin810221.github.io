## 排名是起點，不是答案

公開 benchmark 可以幫你縮小候選，但各任務、語言、資料來源與統計方式不同。把某個總分第一直接選為所有任務最佳，會忽略你的需求。MTEB 將 Embedding 評估擴展到多種任務，是建立這種觀念的重要工作。[MTEB](https://arxiv.org/abs/2210.07316)

先問你要搜尋、分類、聚類、去重還是跨模態。相似度 benchmark 上表現好的模型，不一定在你的問題–文件檢索或短代碼去重上最好。

## 比較表的欄位

| 面向 | 要記錄什麼 |
| --- | --- |
| 品質 | 自有題集、分組指標、錯誤例 |
| 語言與領域 | 繁中、跨語、技術代碼 |
| 輸入 | token 上限、截斷、prompt、模態 |
| 輸出 | 維度、正規化、可支援精度 |
| 執行 | 本機硬體、API、冷啟動與併發 |
| 維護 | revision、授權、資料處理與遷移 |
| 費用 | 匯入、查詢、儲存與額外重排 |

可用性、價格和限制會變；教材不寫死最新排名或單價。保存你實驗當時的模型與價格版本，避免日後比較沒有基準。

## 建立三個公平基線

一個字詞方法、一個小型可本機執行 encoder、一個你能使用的 API 模型，是合理的起步。使用相同來源、切塊、授權和題集，並按各模型文件正確設定 query/document recipe。

不能讓模型 A 看全文、B 被錯誤截斷後再宣布 A 的表示更好；也不能用新文件對舊文件。先排除資料和介面差異，再比較模型能力。

## 維度與參數不要混淆

較高輸出維度增加每筆向量儲存與比較成本，但不一定帶來更高任務分數。模型參數量影響推論硬體，output_dim 影響表示容量，兩者是不同軸線。支援縮短向量的模型也需在所選維度重新評估。

## 小型驗收流程

固定題集、指定成功指標、記錄 p50/p95、測未知和錯誤輸入、比較分組失敗，最後確認遷移成本。如果新模型只改善少數題，卻使部署不可接受，可以保留混合路由或較小模型。

## 長度公平性的一個反例

文件前半段是背景，真正答案在後半段。模型 A 支援的實際輸入較長，模型 B 在前段就截斷；比較時若沒有記錄截斷，容易把資料缺口誤當純表示差異。

你可以採兩種明確實驗：固定相同有效片段，測 encoder 品質；或按各模型最佳可用流程，測整體產品方案。兩者都合理，但問題不同，報告應標示而非混為同一種結論。

## 練習與參考答案

**題目：**模型 A 的公開平均分較高，但你的型號題較差，該選哪個？

**參考答案：**按任務重要性與驗收條件決定，可以選 B、增加精確 lexical 路徑，或分題型路由。公開平均不是你的產品目標，應保存型號反例與模型比較證據。
