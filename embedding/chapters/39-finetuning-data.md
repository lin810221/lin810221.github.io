## 先確認不是管線錯誤

如果問題來自文件未匯入、解析數字錯、prefix 遺漏或權限設定錯，微調不會修好根因。先完成正確 recipe 和基線，再分析 encoder 在哪些題型確實區分不足。

值得微調的情況可能包含領域術語、特定 query/document 關係、短代碼周邊語境或專有分類。但需有足夠且可靠的配對，不把所有同資料夾文件都自動當正樣本。

## 最小資料欄位

```json
{
  "anchor":"國內出差住宿上限是多少？",
  "positive":"國內住宿每晚 2400 元。",
  "negative":"國際住宿依核准計畫。",
  "source_id":"fictional-travel-v1",
  "annotation_reason":"negative 的地區不適用",
  "split":"train"
}
```

這些金額只是虛構示範。資料集需保存版本與標註來源，確認哪些欄位實際送進 loss，哪些只是 metadata。不要讓框架把 ID 或理由錯當另一段訓練文字。

## 切分與近重複

同一文件的改寫問題、近重複段落與新版舊版，最好按群切分。否則模型在 test 看見幾乎相同內容，分數高卻沒有真正泛化。時間、語言和來源切分應對應部署需要。

開發集用於選參數，獨立測試集保留最後評估；持續根據 test 調整就要重新標示它的角色。

## 標註與抽樣

混合容易、一般和關鍵 hard negatives，抽查正樣本是否真正支持答案。保留不確定標籤，必要時讓人審，而不是全部硬轉為 0/1。自動出題可幫擴充，但需驗證答案存在與問法自然。

## 權利與資料處理

確認訓練來源和模型授權符合用途，私人內容進入權重後不容易像資料庫列一樣精確刪除。保存資料依賴和處理政策，訓練前先做不必要敏感資訊最小化。這是資料工程責任，不等於把向量視為匿名。

## 訓練之前的交付

固定一個原模型基線，記錄整體與分組指標、延遲、硬體和失敗案例；再定義希望改善哪組、不允許哪些退步。Sentence Transformers 訓練指南提供資料與 trainer 的入口。[Training overview](https://sbert.net/docs/sentence_transformer/training_overview.html)

## 一次資料審查可以問什麼

正樣本是否真的回答 anchor？負樣本是不適用還是只是另一種正確說法？同一答案群有沒有分到測試？來源是否過期？標註者是否看到足夠上下文？每個問題都可能比增加 epochs 更早決定成敗。

保留少量可解釋的高品質資料先跑實驗，抽查模型最常錯的 hard negatives。擴大資料前確認流程能重現，而非等訓練完成才發現欄位接錯。

## 練習與參考答案

**題目：**有一萬對自動生成資料，比一千對人工確認資料一定好嗎？

**參考答案：**不能只看數量。錯誤配對、重複和領域偏差會影響表示。比較品質、分布與獨立評估，先抽樣查證並保留可信度，而不是把更多資料當成必然改善。
