## 大量匯入多了哪些問題

一百萬份片段無法用兩句範例的方式直接一次送出。需要按輸入數、token 限制、請求大小和速率限制分批，保存狀態與來源映射。數量相同的兩個 batch 也可能有完全不同 token 成本。

先估算每筆長度分布，超長文件明確切塊，保留標題和來源。不能依 byte 或中文字元數聲稱精確符合某模型 token 上限；不同 tokenizer 與前綴都會影響計數。

## 每批保存什麼

```text
job_id、batch_id、input IDs、原始順序、模型設定指紋
狀態：pending → running → validated → committed
錯誤：retryable / invalid_input / permanent_failure
```

回應先驗證數量、索引、維度與數值，再標記 committed。若只成功一部分，應能對缺失項目恢復，而不重複寫入其他資料。穩定 ID 與 upsert 讓相同批次重試具有可控行為。

## 哪些錯誤值得重試

網路暫時中斷、部分服務錯誤或限流可依契約採有限退避與 jitter；空輸入、非法維度、缺金鑰等不應無限重試。回應是否可重試以服務錯誤定義為準，不是把所有 HTTP 非 200 都再送一次。

教材 adapter 不自動重試，避免初學者不知情地重複花費。正式匯入另加有上限的重試層、timeout、進度與錯誤報告。[OpenAI 錯誤與除錯入口](https://developers.openai.com/api/docs/guides/error-codes)

## 併發與非同步

適當併發可提高吞吐，但需控制同時請求數與每分鐘 token。同步 batch 與服務提供的非同步 batch 是不同選項，後者通常需輪詢工作並讀輸出。不要收到 job ID 就把文件標為已完成。

本機推論可依長度分組降低 padding，但仍需把結果還原原始順序。如果排序長度後忘記還原，就會把向量接錯文件；這與 API index 配對是同一種資料身分問題。

## 日誌與敏感內容

記錄錯誤碼、批次 ID、設定與輸入摘要即可支援大部分除錯。完整私人原文、金鑰和 header 不應無條件寫進 log。若需保留原文快照，設定授權與保留期限。

## 練習與參考答案

**題目：**以長度排序匯入，模型回應正常，搜尋卻引用錯文件，可能哪裡出錯？

**參考答案：**檢查排序前後的索引映射與回傳配對。向量數量、維度都正確仍可能錯配。每筆要攜帶穩定 ID，驗收以已知文件內容的查詢確認向量與原文一致。
