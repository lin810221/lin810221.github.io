# DataHarbor 操作與復原手冊

## 正常流程

先驗證整批契約與完整來源區間，再取得 workspace 的單機 writer lock。在同一 DuckDB 交易內寫入原始事件、更新訂單狀態、推進游標與新增 outbox，之後以不可變的版本目錄輸出 Parquet、產生 manifest、讀回核對筆數、paid 總額與 SHA-256，最後原子替換 `current.json` 並確認 outbox。

使用者只跟隨 `current.json` 讀取其 manifest 與 Parquet。不能掃描版本目錄後自行挑名字最大的檔案；未完成發布的檔案不代表可讀版本。manifest 的路徑必須留在 workspace 的 versions 之內。

## 三個中斷點

| 中斷 | 資料庫 | 讀者指標 | 重新執行 |
| --- | --- | --- | --- |
| COMMIT 前 | 維持第一批 | 第一批 12000 | 重送第二批，重新做完整交易 |
| COMMIT 後、指標前 | 已到第二批，有 pending outbox | 仍第一批 12000 | 先恢復 pending 發布，再辨認同批重試 |
| 指標後、確認前 | 第二批尚待確認 | 第二批 11500 | 驗證同版本產物與指標，再確認 outbox |

相同 batch ID 與相同內容雜湊是重試；相同 ID 卻不同內容應拒絕。回補應定義新的輸入契約與驗證，不能把游標往後改回去。程式在處理下一批前先恢復前一次 pending 工作，避免新狀態覆蓋尚未發布的快照。

## 寫入鎖與程序崩潰

`writer.lock` 使用排他建立，只保證同一檔案系統上的單機寫入排除。正常例外由 finally 移除；程序被強制終止可能留下鎖。程式不根據時間自動刪除鎖。人工先確認該 workspace 沒有仍在執行的寫入者，保留診斷資訊，再移除自己的殘留鎖並重跑。跨主機或網路磁碟不能套用此假設，需正式租約與 fencing 契約。

## 損壞與還原

雜湊不符、路徑越界、契約改變或序號缺洞都停止發布，不把資料猜成零。保留來源批次和錯誤，修復資料後重送。沒有實作自動修復受損 Parquet。備份須保存來源、資料庫、一致的指標與其指向版本，並在另一個新 workspace 驗證還原；只看到備份檔存在不算還原測試。

## 保證邊界

本專案驗證程序層的例外與重送，不保證斷電後磁碟持久性、分散式 exactly-once、遠端多寫入者或雲端物件儲存原子 rename。轉用物件儲存時，改用不可變版本及 ETag/版本前置條件寫入，驗證儲存服務自身的一致性契約。正式排程還需要持久狀態、告警、逾時與人工介入程序。
