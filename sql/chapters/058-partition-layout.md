# 分割目錄、Hive欄位與小檔案

目錄結構是資料管理策略，不是索引與交易的替代品。

## 按常用範圍組織檔案

常見結構如 `order_day=2026-11-01/part-001.parquet`，可把日期放進目錄並由支援的讀取器辨識為分割欄位。查詢能否利用這些資訊裁剪，仍取決於讀取選項、條件和引擎。

不要把高基數欄位全部拿來分割，否則可能產生極多小檔案。大量小檔案會增加列舉、開啟、metadata與排程成本，即使總資料量不大，也可能拖慢分析。

## 分割不等於完整性保證

某個日期目錄存在，不代表該日來源都已到齊；某個檔案存在，也不代表它已通過品質檢查。需要另外的來源範圍、完成標記或manifest，避免讀取者把未完成目錄當作正式版本。

## 更新與壓實

改寫小範圍、追加新檔與壓實舊檔都會影響讀取者看到的版本。不要在使用者正在glob的同一個公開目錄裡任意刪改檔案，然後宣稱它等同資料庫交易。專題改採版本化目錄與單一指標，避免讀到半成品。

選擇分割欄位前，列出主要查詢範圍、更新頻率、遲到修正與保留政策，再用相近規模資料量測。這個選擇與SQL的WHERE條件必須一起設計。
