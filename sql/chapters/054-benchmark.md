# 建立有意義的SQL效能實驗

讓結果、環境與測量方法都能被重現。

## 先確認比較的是同一個結果

兩個查詢即使回傳相同筆數，也可能在鍵、空值或金額上不同。先用集合差異、唯一性與指標對帳確認語意相同，再比較效能。把資料少算一半得到的速度，不是可接受的最佳化。

## 記錄實驗條件

保存引擎與驅動版本、資料量和分布、硬體、執行緒、記憶體限制、查詢與索引。說明是否有warm-up、資料或檔案快取，以及如何重複量測。不要只挑最快一次當作代表。

## 成本不只一個時間數字

觀察延遲分布、讀取位元組、輸出列數、暫存磁碟、記憶體與併發條件。不同指標可能互有取捨。開發機的小查詢快，不表示多租戶正式環境的尾端延遲也會符合要求。

## 結論要符合證據範圍

本課計畫實驗可證明SQL在指定引擎執行並產生聚合運算，不能證明某個索引在所有部署都快。若要發布正式效能結論，應附原始量測與資料生成方法，並清楚列出未測的情境。

每次只改一個主要假設，保留前後計畫，才能將改善連到原因。若資料量、設定與查詢同時改變，就應承認無法單獨歸因，而不是把所有差異都歸功於最後改的一行SQL。

## 可執行查詢

以下是下載包 `queries/17.sql` 的實際內容；先由 `fixtures.seed` 建立本課合成資料。執行入口會建立獨立資料庫，不需修改既有資料。

```sql
EXPLAIN ANALYZE SELECT customer_id,SUM(amount_cents)
FROM orders WHERE status='paid' GROUP BY customer_id;
```
