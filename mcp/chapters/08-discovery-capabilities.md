# 探索與能力協商：先知道對方會什麼

用 server/discover 理解新版連線，並為不支援的能力設計降級路徑。

## 探索的目的

`server/discover` 回傳 Server 的支援版本、能力與可選的實作資訊。現代協定要求 Server 提供這個方法，但 Client 不一定每次先呼叫；若已知版本，也能直接送出自足請求。Python 的 auto 模式會先探索，讓一般應用不必手寫相容流程。

探索不等於讀取全部工具，能力也不等於使用者授權。`tools` capability 告訴你這個服務懂工具介面；`tools/list` 才列出這次身分可見的工具；真正呼叫時仍需驗證該主體是否有操作資源的權限。

## 能力是互通契約

| 能力 | 應用可安排的行為 |
| --- | --- |
| tools | 列舉及呼叫工具 |
| resources | 列舉及讀取資源 |
| prompts | 列舉及渲染模板 |
| completions | 對模板或參數提供補全 |
| elicitation | 在支援流程內請求使用者輸入 |

這張表不是「所有 Host 必定都有」。實際的訂閱、擴充與個別方法還要查看對應細項。若 Client 沒宣告某個能力，Server 不應假設可以要求 Client 執行它；Host 也不應在 UI 承諾它無法呈現的互動。

## 不支援時怎麼處理

若對方不認得現代探索，SDK 可在 auto 模式退回舊握手。若對方支援探索但沒有你需要的資源讀取，則應顯示能力不支援，或使用事先定義的替代工具；不能把同名 HTTP 路徑當成協定替代品。對未來新增的未知可選欄位保持容忍，對必要輸入則明確驗證。

在自己的 Host 中，可以先建立能力檢查表：哪些是完成任務不可缺少，哪些只是改善使用體驗。例如搜尋摘要是必要，Prompt 補全是選用。只有必要能力欠缺時才阻止該流程，避免因為一個選用功能不存在就關閉整個服務。

## 身分會影響工具可見性

同一個 Server 可以根據本次授權列出不同工具，因此工具清單快取不能只以 URL 為鍵。另一方面，同一授權和同一修訂下應保持清單穩定，避免模型的上下文與實際可呼叫契約在對話中不斷漂移。清單變更後，也要有失效與重新探索機制。

## 練習與解答

Client 連線成功但 `resources` 為空，是否代表 Server 壞掉？不一定，可能它只提供工具。解答應先看服務宣告與目標需求。若任務必須讀文件而 Server 沒提供資源，應使用其公開搜尋／讀取工具或換用適合的 Server，不能自行猜測內部文件位置。
