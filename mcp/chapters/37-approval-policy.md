# 審核政策：誰可以決定哪一個操作

把模型提案、Host 確認與業務核准分成可追查的狀態。

## 先定義需要核准的變更

查詢公開文件、讀取內部工單、關閉工單、刪除資料與付款，風險與授權需求不同。應按具體業務決定政策，而不是所有動作都彈一樣的確認框。審核者應看得懂「會改哪個資源、從什麼變成什麼、何時失效」。

模型產生呼叫不代表使用者已核准；使用者曾要求一個目標，也不表示所有可能達成目標的副作用都已獲授權。Host 可以幫忙呈現提案，Server 則應持有可查驗的核准事實。

## 兩種確認可能並存

供應商工具確認控制是否允許這次遠端呼叫；業務審核控制是否允許改變某張工單。若只有前者，另一個直接使用 MCP Client 的呼叫者可能繞過 UI。重要變更應在 Server 或共享業務服務中檢查，不依賴單一 Host。

本課把 `review()` 放在內部 operator 介面，不註冊成模型可呼叫工具。模型不能靠呼叫另一個 approve 工具，自行取得原本需要人的核准。

## 狀態機比布林值完整

```text
pending → approved → consumed
       ↘ denied
任何未使用狀態都可能因期限到期而失效
```

approved=true 這種由模型直接傳入的參數，沒有說明誰批准、批准什麼、期限多久與是否已用過。狀態機則能把每個轉移綁定到可信事件，並拒絕不合理的跳躍。

## 分離提出者與審核者

本課採兩人政策：提出者與審核者不能相同，審核者還需 tickets:review 且屬同一租戶。這是教學業務規則，實務可以依風險選不同政策，但無論如何都應明確實作與測試。不能只在 UI 隱藏自己核准按鈕，後端卻仍接受。

## 練習與解答

未核准時提交，應被拒絕且工單仍 open；可信審核者核准後，才允許同一預覽結案。把 ALICE 的 scopes 增加 review 仍不能自行核准，因為此專題另外要求不同 subject。這展示「有角色」與「符合此次核准政策」也可能不同。

## 可執行範例
