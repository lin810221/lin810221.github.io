# 並行、呼叫數與結果預算

把 Agent 和工具服務的資源使用量限制在可維護範圍。

## 非同步不代表無限並行

一次啟動一千個工具呼叫，可能耗盡連線池、檔案描述符、記憶體或上游配額。即使每個函式都是 async，也應設定全域與每租戶的並行上限、等待佇列和總任務預算。公平性也是設計的一部分，避免單一租戶佔滿全部資源。

本課使用 Semaphore 限制同時執行數，並在 finally 釋放 active 計數。測試同時檢查峰值與結束後數量，避免只看到所有任務完成，卻漏掉例外時資源未釋放。

## 容量估算的直覺

在穩定條件下，Little's Law 提供平均在途量的近似：

$$
L\approx\lambda W
$$

若每秒 10 次請求、平均等待 0.5 秒，在途量約 5。這不是保證最適並行數，因為尖峰、長尾、重試與上游限制都會影響實際容量。它可作為開始量測的基準，再用壓力測試調整。

## 模型與工具共同花費預算

工具清單與結果使用模型上下文，工具本身可能使用網路、CPU 或付費 API。因此至少要限制模型回合數、每回合工具數、單次結果 bytes、總結果 bytes、單次時間與任務 deadline。不要只用 token 上限就宣稱控制了整個 Agent 成本。

大結果應提供分頁、摘要或可授權引用，不應直接截斷 JSON 到無法解析。若只回傳部分資料，結果應有清楚的 truncated 或 pagination 語意，避免模型把不完整集合當成全部。

## 並行寫入需要業務判斷

兩個查詢可以並行，不代表兩個互相依賴的寫入也可以。預覽與提交有先後關係；同一資源的不同變更可能需要版本檢查或鎖。Host 不應因為模型同時提出兩個呼叫，就無條件把它們放進 gather。

## 練習與解答

執行八個虛構任務、並行上限二，峰值應等於二且結束後 active 為零。再讓其中一個任務失敗，資源仍應釋放。若你的服務將等待佇列設成無限，雖然 active 有上限，記憶體仍可能被等待中的任務耗盡，因此還需 admission control。
