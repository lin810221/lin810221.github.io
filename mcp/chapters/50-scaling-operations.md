# 擴展與維運：無狀態協定仍有應用狀態

處理多 worker、共享收據、訂閱、容量及安全停止。

## 無狀態的是哪一層

現代 MCP 請求自帶版本與能力，不需要用協定 Session 記住這些資訊。但資料庫、審核、冪等收據、應用 job 和訂閱仍然有狀態。不能因為協定無狀態，就把所有資料放在單一 worker 記憶體，再期待多副本自動一致。

本課專題用 SQLite 表達交易不變量，適合本機學習。真正多節點部署需選擇共享且符合負載需求的資料庫，確認唯一鍵、交易隔離、備份與恢復；不同容器各保存一份本機 SQLite 不會自然共享收據。

## 多輪輸入與多 worker

若 MRTR 的 request state 需要驗證或解封，多副本必須遵守相同安全政策並管理所需金鑰。若續輪被送到另一台，仍應能驗證主體、狀態期限與原始操作。粘性路由可以解某些問題，但不能拿來取代持久與安全設計。

舊 Client 的 Session 支援也可能帶來額外路由需求，因此部署矩陣需包含協定模式。你可以先只對特定 Host 版本提供服務，但要明確寫出，而不是遇到某個 Client 偶發失敗才猜它是不是走舊版。

## 訂閱與重新同步

訂閱串流會因網路、部署或過期終止。Client 應能重連並重新讀取必要目錄或資源；Server 若多副本共同服務變更通知，需考慮共享事件或失效機制。只在產生變更的 worker 發送記憶體通知，可能漏掉其他 worker 的訂閱者。

## 限制與公平性

依租戶限制同時請求、佇列長度、結果大小與上游預算，並量測拒絕與等待時間。容量不足時回傳可辨識的暫時失敗，比無限排隊直到整個服務耗盡更容易恢復。高成本工具可使用獨立 worker 或佇列，不必和快速搜尋共享完全相同的執行池。

## 安全停止與恢復

部署更新時先停止接受新工作，給已開始的請求合理時間，取消不必要任務並清理連線。對結果未知的寫入，依收據與上游查詢恢復，而不是在重啟時無條件重做。定期演練資料庫恢復與金鑰輪替，才能知道重現環境以外的維運是否完整。

## 練習與解答

兩台服務各有一份記憶體 idempotency dict，同一操作分別送到兩台，是否只執行一次？不保證。解答是把收據與業務效果放在可協調的持久交易邊界，或使用上游提供的等價能力，而不是只增加更多 worker。
