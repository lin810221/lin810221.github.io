# 冪等鍵、交易與執行收據

在重送、並行與回應遺失時，保證同一操作不會重複產生效果。

## 重送是正常情況

網路可能在 Server 寫入後中斷，Client 不知道操作是否完成。若直接換一個請求再執行，可能重複付款、寄信或更新。冪等設計讓同一業務操作重送時回傳相同收據，而不是再產生一次效果。

$$
F(x,k)=y,\qquad F(x,k)\text{ 的重送只讀取原收據 }y
$$

鍵 k 必須綁定操作與主體。不同內容使用同一鍵應拒絕，不能把原本 A 操作的收據當成 B 操作成功；不同租戶也不應分享相同收據空間。

## 與 JSON-RPC ID 不同

JSON-RPC ID 關聯請求回應，冪等鍵則關聯業務效果。每次重送可以有新的請求 ID，但仍使用同一個 idempotency_key。鍵的保存期限、碰撞規則、重送回應與失敗語意都應是工具契約的一部分。

本課 key 綁定 issuer、tenant、subject，並保存 preview_id 的摘要。相同綁定與相同預覽回傳舊結果；同鍵不同預覽拒絕；已用預覽換新鍵也拒絕。

## 把效果與收據放在同一交易

本課同一個 SQLite 交易包含：檢查收據、驗證預覽、條件式 UPDATE、插入收據、消耗預覽及 committed audit。中途失敗就回滾。若先提交業務效果，稍後才另寫收據，就會留下「已改變但無法證明」的窗口。

在真實外部系統中，本機資料庫交易無法包住另一個遠端付款 API。這時需要上游提供冪等能力、outbox、可查詢操作狀態或補償流程，並明確說明無法保證的部分，不能用一個本機字典宣稱跨系統 exactly-once。

## 並行與權限撤銷

兩個 Client 同時用同一鍵提交，資料庫唯一性與交易序列化必須保證只產生一次效果。讀收據前仍檢查目前必要權限，避免已撤權者透過重送讀到不再可見結果。正式收據回傳政策還應符合資料保存與刪除要求。

## 練習與解答

執行兩次同鍵提交，預期工單 version 只從 1 變 2，committed audit 只有一筆。再在 UPDATE 後、寫收據前注入例外，應回復原狀且沒有收據。這些是檢查資料事實的測試，不是只確認畫面出現「成功」。
