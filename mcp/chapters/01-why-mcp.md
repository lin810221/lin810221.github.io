# MCP 解決什麼問題：從模型回答到系統能力

先分清楚模型、工具與整合協定，建立這門課要解決的工程問題。

## 從一個真實需求開始

假設你要讓助理回答「工單 T1 為什麼還沒關閉」，並在你確認後結案。模型本身無法知道公司工單的最新狀態；把使用手冊放進提示詞，也不會讓模型取得資料庫連線。應用程式必須提供查詢與更新能力，並決定誰可以用、何時可以執行，以及結果如何回到對話。

最直接的做法，是為每個應用各寫一套工具介面。當第二個桌面助理、第三個 Agent 或新的模型加入，連線設定、參數格式、工具清單及回傳解析便開始重複。MCP 把這一層互通介面標準化，讓同一個能力提供者能被多個支援協定的 Host 使用。

## 它標準化哪些事情

MCP 定義探索工具、讀取資源、取得提示模板及交換訊息的方法，也定義版本、能力、傳輸和授權等規則。工具仍然由你的程式執行，業務邏輯仍然由你維護。協定不會替你判斷一張工單可不可以關閉，也不會替模型保證回答正確。

| 層次 | 工單助理中的責任 |
| --- | --- |
| 模型 | 解讀問題、提出工具呼叫、整理結果 |
| Host | 提供對話、連線、工具選擇與使用者互動 |
| MCP Client | 將探索與呼叫轉為協定請求 |
| MCP Server | 提供工具、資源與可驗證的契約 |
| 既有系統 | 保存工單、使用者與交易事實 |

## 與 Function Calling、RAG 的關係

Function Calling 是模型服務表達「想呼叫哪個函式」的介面；MCP 是應用程式與能力伺服器之間的介面。Host 可以把 MCP 的工具描述轉為供應商接受的函式定義，再把模型產生的參數交給 MCP Client。兩者可以串接，卻不是同一層協定。

RAG 則是一種先檢索、再生成的應用流程。檢索可以由普通函式完成，也可以由 MCP 工具完成。將搜尋包成 MCP 不會自動獲得切塊、重排、引用或檢索評估，這些仍需自行設計；需要完整原理可連到 [RAG 課程](../rag/index.html)。

## 什麼時候值得導入

當能力需要被不同 Host 重用、工具團隊與模型團隊分開維護，或你希望明確列出支援版本與契約時，MCP 很有價值。只有單一程式的一個內部函式時，也可以先使用直接呼叫，再在邊界成熟後加入協定介面。選擇的依據是維護成本與互通需求。

## 練習與解答

把「查工單、總結原因、確認結案、寫入結果」分配到上表。解答：查與寫由 Server 包裝既有系統能力；總結由模型處理；確認的介面由 Host 呈現，執行資格則必須由伺服器和審核紀錄驗證。只在提示詞寫「請先確認」不足以形成可強制執行的權限邊界。
