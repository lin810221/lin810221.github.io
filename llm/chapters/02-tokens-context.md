## Token 不是固定的一個字

Token 是模型處理的離散單位，可能是一個字、一部分詞、標點或其他編碼。不同模型使用不同 tokenizer；中文、英文、程式碼與表格的切分方式也不同。

因此「一個中文字必定一個 token」或「四個字元固定一個 token」都不能當成計費或容量契約。正式估算應使用供應商的計數能力，實際結算則看回傳的 usage。

除了使用者文字，system 指令、歷史、工具 schema、檢索文件及多模態內容都可能占用輸入預算。模型可見的資料範圍，不等於畫面上最後一則訊息的長度。

## 生成的核心：根據前文預測後續

對典型自回歸語言生成，可用條件機率表達：

$$
P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_1,\ldots,x_{t-1})
$$

模型逐步產生後續 token。這能形成流暢答案，但流暢不等於已查證；看似合理的引用、日期或函式名稱仍可能錯誤。

這個公式是理解文字生成的簡化模型，不是所有圖片、音訊或影片生成架構的完整描述，也不能用來推定某家服務的內部細節。

## 上下文視窗與輸出預算

上下文視窗描述單次推論可處理的範圍。簡化理解是輸入、輸出及相關推理開銷必須符合模型與介面的容量規則。最大輸出還可能有獨立限制，不能把整個 context window 全當成答案長度。

模型提供長上下文，不代表把所有資料塞進去就一定找得到關鍵條件。位置、資訊噪音、文件衝突及任務難度都會影響結果。需要精準回答時，檢索與資料篩選仍有價值。

## 訓練、推論、RAG 是不同事情

| 做法 | 改變什麼 | 常見目的 |
| --- | --- | --- |
| 預訓練 | 大規模更新模型權重 | 建立通用語言與其他能力 |
| Fine-tuning | 用特定資料調整可訓練模型 | 特定格式、風格或任務行為 |
| Prompt / Context | 改變本輪提供的指令和資料 | 告訴模型這次要做什麼 |
| RAG | 執行時先查資料再提供上下文 | 使用可更新、可追溯的知識 |
| 應用記憶 | 保存並召回使用者或工作資料 | 延續對話與個人設定 |

今天在 API 送一份文件，通常不代表模型因此永久學會它。保存對話、訓練權重和把文件加入檢索索引，是三種不同操作。

## 為什麼知識可能過時？

模型訓練資料有時間與範圍限制。即使最新模型，也不能假設每個回覆都即時查網路。對價格、法規、規格和時程，應加入可信來源或搜尋，再驗證來源日期。

如果供應商提供搜尋工具，必須確認這次請求是否真的啟用並執行，不能因為模型說「我搜尋了」就視為已有工具紀錄。

## 怎麼把這些觀念用在設計上？

保留原始問題，選取必要上下文，限制單輪輸出，記錄 usage 和結束狀態。若輸入過大，先分段或檢索；若輸出被截斷，處理 incomplete，而不是把前半段當成完整資料。

**練習：**替一個客服任務列出會占輸入 token 的項目：規則、最近對話、工具 schema、訂單資料。再說明哪些需要每輪提供，哪些可按需取得。
