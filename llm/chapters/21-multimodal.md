## 多模態不是一個開關

圖片理解、圖片生成、PDF 解析、影片理解與音訊生成是不同能力，需要對照具體模型、介面與工具。模型接受圖片，不代表同一請求就能輸出圖片；聊天產品能處理某檔案，也不代表原始 Messages API 接受相同格式。

先定義輸入媒體、任務、需要保留的定位資訊和輸出，再挑選服務能力。

## 內容區塊怎麼表達？

| 介面 | 常見圖片輸入形狀 | 需核對 |
| --- | --- | --- |
| OpenAI Responses | input content 中的 input_image | URL、檔案 ID、data URL 與 detail 支援 |
| Gemini Interactions | image 等內容型別 | mime_type、內嵌資料或檔案引用 |
| Claude Messages | image block 與 source | media_type、base64 或支援的引用形式 |

不要把本機檔案路徑字串直接交給遠端 API，期待它能讀到你的硬碟。通常需要上傳、編碼或提供服務能存取的資源引用。

## 圖片的資訊與成本

解析度、裁切和文字大小會影響結果與處理用量。對整張報表，可以先定位需要的區域；若只問一個小欄位，整批高解析度圖片可能增加成本而沒有幫助。

模型可能看錯數字、小字或圖例。對需要精準計算的表格，可結合 OCR / 文件解析與程式計算，再讓模型解釋。不要只因為答案語句完整就相信每個數值。

## PDF 與文件理解

PDF 可能包含可選取文字、掃描影像、複雜表格或跨頁內容。支援直接 PDF 的服務有自己的頁數、大小與模型條件；也可以先自行解析再切塊。

保留來源、頁碼、區塊位置和版本。讓回答能引用「哪份文件哪一頁」，比只回傳一段無法定位的摘要更容易查核。

如果先轉成純文字，圖表與版面可能遺失；若完全依視覺理解，數值與結構也需要驗證。選擇取決於任務，不是檔案副檔名。

## 影片與時間資訊

影片理解通常涉及影格、時間戳、音訊和處理取樣。問「哪一秒出現某事件」時，需要保留時間對應；少量抽樣畫面不代表看過每一幀。

對長影片，可先分段、取得事件索引或相關片段，再進行精細理解。輸出要表達時間精度與來源，不要偽裝成逐幀的完整檢查。

## 理解和生成分開驗證

圖片 / 音訊 / 影片生成有不同模型、工具、回傳形式與可能的非同步工作。輸出應記錄來源和生成設定。若任務是科學圖或精確圖表，通常應讓程式依資料繪製，再使用模型協助解釋。
