## 用量不是文字長度

模型請求可能包含規則、歷史、工具 schema、文件及多模態內容；輸出也可能包含思考、工具提案和文字。依供應商與介面讀取 usage，再映射到自己的計費項目。

不要只用畫面上的答案字數估價。多輪 Agent 每次模型與工具呼叫都可能增加成本，即使最後只有一小段回答。

## 一個明確的成本模型

以下假設已將 usage 正規化：總輸入 I 包含其中快取部分 C，輸出 O 的計價定義已確認。

$$
\operatorname{cost}=\frac{(I-C)p_{in}+C p_{cache}+O p_{out}}{10^6}
$$

這不是三家所有方案的完整帳單公式。快取寫入、儲存、搜尋、音訊、影像、工具與背景執行可能另計；某些 usage 細項也不能重複相加。

## 預算要在多個層次限制

限制單次輸出、單輪 Agent 回合數、工具次數與整體時間。對帳號或工作佇列也可以設定日 / 月預算與使用者配額。

max_output_tokens 只限制該請求的生成，不會自動限制整個 Agent 六輪的累積費用，也不會限制工具本身的外部花費。

## 延遲由哪些部分組成？

分清首字 / 首個音訊時間、整體生成時間、工具等待、佇列及人工審核。串流可以更早顯示進度，但不必然縮短完整工作的完成時間。

平行獨立查詢可能縮短等待，但不會自動減少呼叫數或 token。若多個分支都讀相同資料，應先檢查是否真的有額外價值。

## 模型路由的合理方式

可以將簡單任務交給低成本候選，複雜或驗證失敗才升級；但升級規則要可測。例如 schema 解析失敗、缺少必要來源或確定工具能力不符，可以觸發明確路徑。

不要只用未校準的模型信心分數切換。先建立資料集，比較品質門檻、升級比例和總成本，避免兩次呼叫比一次合適模型更貴。

## 如何做公平比較？

固定資料、工具與驗收條件，記錄模型版本、推理設定、usage 和實際時間。比較完成同一工作所需的總成本，而不是只看單位 token 價格。

**練習：**假設 80% 任務可用小模型完成，剩下升級。將第一次失敗的費用也納入，計算何時比全部用大型模型划算。
