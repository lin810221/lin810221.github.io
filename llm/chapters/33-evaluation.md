## 測試正確性和評估模型品質

程式測試驗證固定契約，例如工具白名單、ID 配對、未核准不發布。模型評估則量測真實資料上的回答、工具選擇或引用品質。離線測試通過不代表真模型在所有任務都正確。

兩者都需要，但不應互相代替。先把可確定的規則測好，再把費用花在真正需要模型的評估。

## 本課的離線測試

從 llm 資料夾執行，不需要安裝 pytest：

```powershell
python -m unittest discover -s examples -p test_examples.py -v
```

測試包含三家 body 欄位、可見文字解析、截斷、乾跑不連線、JSON 來源驗證、工具預算、原生歷史簽章保留、記憶隔離與核准去重。

網路呼叫以 mock 替換。這能證明程式按預期建構與處理協定，但不能保證你的帳號或特定模型支援所有功能；真正上線前仍要做小規模整合驗證。

## 怎麼建立評估資料集？

每題保存輸入、可用資料、期望行為、必要來源或工具，以及不能做的事。除了正常題，也要有無答案、資料衝突、錯誤工具結果、重試與邊界規格。

資料集應涵蓋真實使用情況，並保留獨立測試集。不要把同一批答案直接放進 prompt 範例，又用它宣稱泛化表現。

## 分開量測的指標

| 層次 | 指標例子 |
| --- | --- |
| 檢索 | 必要文件召回、權限過濾、資料新鮮度 |
| 生成 | 答案支持度、完整性、無依據拒答 |
| 結構 | JSON 與 schema 成功率、截斷率 |
| 工具 | 選擇正確率、參數正確性、實際成功率 |
| 執行 | 迴圈數、失敗恢復、人工等待與完成率 |
| 資源 | 首字延遲、整體時間、token 與工具成本 |

格式成功率很高仍可能事實錯誤；工具被呼叫也不代表工作完成。每個指標都應對應具體產品需求。

## 模型評分可以怎麼用？

可讓評分模型依清楚規則輔助檢查，但需抽查與校準，尤其避免同一模型只憑語氣給自己高分。能用程式驗證的 ID、數字、格式或工具紀錄，先用程式驗證。

對開放式答案，使用明確 rubric，例如「每項主張有來源」、「不能超出資料」、「缺條件需澄清」，比只有一個總分更能定位問題。

## Tracing 和可觀測性

記錄模型與版本、prompt 版本、request / run ID、工具名稱、耗時、usage、停止原因和錯誤類別。對敏感資料做必要的欄位處理，不要預設把所有輸入和憑證送進追蹤系統。

更改模型、工具 schema、檢索器或推理設定後，重跑相關資料集。若只是 UI 文案修改，不需要重新呼叫付費模型。

**練習：**為完整專案加三題資料：有依據、無依據、引用錯誤。先用 deterministic baseline 驗證路由，再比較真模型的答案支持度與成本。
