## 先分清四種語音需求

| 需求 | 輸入與輸出 | 常見設計 |
| --- | --- | --- |
| 轉錄 ASR | 錄音 → 文字 | 上傳檔案或串流音訊 |
| 語音合成 TTS | 文字 → 音訊 | 指定語音與可用格式 |
| 音訊理解 | 音訊 → 分析或回答 | 保留說話內容與其他聲音線索 |
| 即時對話 | 持續雙向音訊 | 即時 session、打斷與事件同步 |

聊天網站的語音功能不能直接證明某個文字 API 提供全部四種能力。請依供應商的音訊 / Realtime / Live 模型和端點查核。

## 分段流水線或原生語音互動

可以用「ASR → 文字模型 → TTS」組合，容易觀察與替換，但多段處理增加延遲與格式轉換。支援的原生即時介面可以直接交換音訊，但也有 session、工具與事件協定要管理。

產品還需要定義錄音何時開始、誰能打斷、什麼時候算一句說完，以及連線中斷如何恢復。這些不是調 temperature 就能處理。

## WebRTC、WebSocket 與短效憑證

OpenAI Realtime 和 Gemini Live 各有支援的傳輸與用戶端整合方式。瀏覽器直接連接時，應由可信後端建立適當的短效憑證或 session，不要把長期 API Key 放進前端。

```text
瀏覽器 → 已認證後端 → 建立受限即時憑證 / Session
       → 依官方支援方式連接即時服務
       → 接收音訊、文字、工具及結束事件
```

此圖是架構說明，不是通用的跨供應商認證格式。每家 session 設定、到期規則和工具協定必須個別查核。

## VAD 與打斷

Voice Activity Detection 協助判斷說話開始與結束，但吵雜環境、停頓和多人聲可能影響判斷。介面可以提供按鈕控制作為補充。

使用者打斷時，要同步停止播放、決定是否取消遠端生成，並維護對話實際已聽到的內容。播放了兩秒，不代表模型整段回答都應視為已傳達。

## 音訊格式與工具

注意取樣率、聲道、編碼、chunk 邊界與時間戳；格式不符會造成雜音、速度錯誤或服務拒絕。延遲也要分為收音、網路、模型、工具和播放，不只是生成 token 速度。

即時模型要求查庫存或修改預約時，仍是工具提案。低延遲不能取代授權與審核；對重要動作可以先用口頭或 UI 確認，再由後端執行。

## 如何評估？

除了文字正確率，評估轉錄錯字、首個音訊延遲、打斷行為、工具完成率與斷線恢復。對語音生成，也要確認所用聲音與內容符合產品需求與權限。
