## 服務邊界比一個 client 物件更大

正式應用需要認證、請求驗證、使用者資料隔離、模型與工具執行、持久狀態、可觀測性及錯誤回應。把 API Key 放進前端再直接呼叫模型，會讓憑證與控制都暴露。

```text
前端 → 應用 API → 認證與輸入驗證 → 工作 / Agent 執行
                       ↓                ↓
                  資料權限          供應商與工具
                       ↓                ↓
                  狀態與審核 ← 結果驗證與事件
```

## 設定與憑證

Key 放在服務端的設定或秘密管理系統，使用符合環境的範圍與輪替方式。開發、測試和正式環境分開，避免一次測試耗盡正式配額。

模型、API 版本、prompt、工具 schema 和輸出契約都要有可追蹤版本。升級前用資料集驗證，不要只因為別名指到更新模型就假設行為不變。

## 同步、串流或背景工作

短工作可以同步回應；需要即時顯示進度可以串流；長工作與人工審核適合回傳穩定 run ID，讓前端稍後取得狀態。

等待人核准時，不要保持 HTTP 連線數小時。保存具體提案、狀態與版本，之後由受權請求續接。Webhook 或佇列都要處理重送與去重。

## 資料保存的不同層次

分清供應商的 response / interaction 保存、操作日誌、濫用監控、訓練用途、你自己的資料庫與追蹤系統。單一 store=false 不代表所有層次都使用相同政策。

資料期限、區域、企業設定和方案可能不同，應查你使用的確切服務與帳號條款。不要用另一家雲端平台或聊天產品的說明取代目前 API 的條件。

## 外部動作與恢復

模型生成完成後，仍要驗證資料與權限。涉及寄信、交易或發布，先建立提案，再執行有穩定業務 key 的動作。工作者崩潰後應可辨認哪些已完成、哪些仍等待。

SQLite 適合本課單機範例；多實例服務需要適合的資料庫、交易與併發策略。單一 Python 字典或 process 記憶體不能自然跨多台機器共享。

## 上線驗證要包含失敗路徑

檢查無效憑證、無權限資源、限流、截斷、工具失敗、重複核准、程序重啟與前端斷線。確認對外錯誤訊息可理解，內部仍有足夠 request ID 與紀錄診斷。

健康檢查不應每次都呼叫昂貴模型。可將本地存活、資料庫就緒與供應商整合的監控分開。

## 發布與回復版本

保留上一版可用設定，對既有 session 和待審提案維持相容。改動欄位、工具或 interrupt 順序時，先規劃舊工作如何完成，而不是只部署新程式。

**練習：**畫出完整專案的服務版，標明哪些在 API 程序、哪些在工作者、哪些保存在資料庫，以及每一項資料何時刪除。
