## Agent 是一個受控制的迴圈

在本課，Agent 指能依任務與當前觀察，選擇下一個工具或步驟的系統。它通常有模型、工具、狀態、執行器與停止條件，不只是一次文字生成。

```text
目標 → 模型決策 → 工具提案 → 驗證與執行 → 新觀察
             ↑______________________________|
             └→ 最後答案 / 等待人 / 無法完成
```

模型不必掌控每個步驟。對金額計算、權限、固定政策等可確定的條件，用程式與可信資料處理，會更容易驗證。

## Workflow 和 Agent 如何分工？

固定 Workflow 由程式決定路線；Agent 將部分選擇交給模型。可以在固定流程中只放一個 Agent 節點，也可以在 Agent 中呼叫固定子流程。

例如「檢索 → 草稿 → 審核」可以完全固定；「這個問題需要檢索還是計算」可以讓模型選擇。重要的是決策邊界清楚，而不是自由度越高越好。

## 最小架構的五項責任

| 元件 | 責任 |
| --- | --- |
| 模型 | 根據任務與觀察提出下一步 |
| 工具目錄 | 描述可用能力與參數 |
| 執行器 | 驗證、授權、執行與回傳結果 |
| 狀態 | 保存任務、歷史、進度和必要識別 |
| 控制政策 | 停止、預算、審核、失敗與恢復 |

若沒有執行器，模型只是描述工具；若沒有狀態，長工作難以續接；若沒有停止條件，可能反覆耗費時間和 token。

## 自主程度應按任務設計

先讓 Agent 做唯讀查詢或提出草稿，再逐步加入受限動作。對重要操作，用具體提案、外部核准與穩定執行識別。不要讓一句「請自主完成」繞過所有檢查。

工具回傳資料也可能有錯或被注入指令。把它當觀察，不是新的最高權限規則。模型的規劃和行動都要在應用允許範圍內。

## 何時不需要 Agent？

固定表單抽取、明確計算、短步驟檢索問答或已知路由，可能用普通函式或固定圖就足夠。Agent 帶來的是彈性，也增加不確定性、成本與評估負擔。

只有當任務確實需要依中間結果調整工具或路線時，再加入模型選擇。先建立簡單基線，才能知道複雜架構是否真的有收益。

## 完成的定義

Agent 不應只在模型說 done 時算成功。檢查輸出契約、必要資料、工具紀錄和任務條件；若仍等待審核，標示 waiting；若預算用完，標示 budget_exceeded。

**練習：**把一個「訂單查詢與退款助理」分成唯讀工具、模型判斷、人工核准和固定交易四部分，指出哪些權限不能由模型自行給自己。
